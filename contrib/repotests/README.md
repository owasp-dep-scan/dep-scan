# Repo-test data

The pre-generated BOMs, atom slices and OpenAPI files the repo tests scan,
served as OCI artifacts from `ghcr.io/owasp-dep-scan/depscan-testdata`,
pushed and pulled with [oras](https://oras.land). One artifact per project
and generation; each file is one layer, so every file can be checked by
digest, and the manifest carries the source repository, commit, cdxgen,
atom and cdxgen-plugins versions, the cdxgen arguments and the generation
date as annotations.

## Layout

- `projects.json` declares every project: its name, language directory, Git
  URL, a full pinned commit (never a branch or a tag), the project types,
  the cdxgen arguments, and what the tests expect from the data
  (`minReachablePurls`, `mustReach`). A project is generated by running
  cdxgen once per type with those arguments, which produces
  `sbom-<type>.cdx.json`, `<language>-reachables.slices.json`,
  `<language>-usages.slices.json`, `<language>-callsites.slices.json` and,
  where endpoints were found, `<language>-openapi.json` files.
- `generate.sh NAME SRC_DIR OUT_DIR` clones the pinned commit and runs that
  generation, then writes `generation.json` with the provenance of the run
  (`write_provenance.py`). It executes the project's build tooling, so it
  runs only in the generate job, which holds no write token, or
  deliberately on a workstation.
- `validate.py` is the validator; the same checks run in the producer and
  the consumers:
  - `staleness DATA_DIR --projects projects.json --name NAME` refuses BOMs
    generated by a cdxgen older than 13.8.0, reachables slices in the atom 2
    shape (dep-scan's slice reader skips them silently, which is how a whole
    generation of test data used to scan as if empty), and slices without
    one flow carrying a `pkg:` purl. A project with `minReachablePurls` 0
    records that its slices carry no package identity: C and C++ code has no
    purls to attach, in atom 2 as in atom 4, so those projects need at least
    one flow at all instead.
  - `assert ... ` also runs the reachability analyzers over the data
    directory, exactly as a `depscan scan --target-kind bom-dir` run does, and
    fails below `minReachablePurls` or when a `mustReach` package name is not
    reached.
  - `digests DATA_DIR --manifest MANIFEST.json --digest sha256:...` checks
    that the manifest hashes to the digest the lock file pins, then
    verifies a pulled artifact file by file against its layer digests.
  - `lock --data-root DIR --lock-out FILE --registry REGISTRY` writes the
    lock file from the `generation.json` records and the OCI descriptors
    fetched after pushing.
- `testdata.lock.json` maps each project to the manifest digest of the
  generation the tests consume. Consumers pull
  `ghcr.io/owasp-dep-scan/depscan-testdata@sha256:...`, never a tag, so a
  new generation reaches the tests only through a pull request that changes
  this file.
- `.github/actions/repotests-data` is the consumer entry point: it installs
  oras, restores an `actions/cache` cache keyed by the digests it is asked
  for, pulls what is missing by digest, verifies every file's digest with
  `validate.py digests` and runs the staleness checks.
  `.github/scripts/repotest-project.sh NAME` copies one project into the
  reports layout, runs the depscan scan the repo tests use and asserts the
  reachable purl floor and `mustReach`.

## Generated-input caches in CI

The projects the repo tests used to generate on every run
(`java-sec-code`, `dotnet-podcasts`, `vulnerable-aws-koa-app`, the
`dejacode` scan and the dep-scan self scan in
`.github/workflows/repotests.yml`) now keep their cdxgen and atom outputs
in `actions/cache` entries, so a pull request re-scans restored inputs
instead of regenerating them. The caches hold only what cdxgen and atom
wrote into the reports directories: the `*.cdx.json` BOMs, the
`*slices*.json` atom slices, the `*openapi*.json` spec files, cdxgen's
`*.introspection.json` reports and a `generation.json` when one exists.
dep-scan's own outputs (the VDR, the risk and license reports, the findings
and manifest documents and the analysis fallback reports) are never cached;
every run re-derives them, because that analysis is what the jobs exist to
test.

There is one entry per scan variant: `java-sec-code` and `dotnet-podcasts`
have three each (plain profile, research profile with
`FrameworkReachability`, research profile with `SemanticReachability`), the
koa app, dejacode and the self scan have one each. On a restore hit the job
runs `depscan scan <restored dir> --target-kind bom-dir` with the same
reachability and explain options the full run uses, and skips the project's
build steps (`dotnet build`, dejacode's `docker build` and `uv pip
install`), which produce only what cdxgen reads for the BOM. On a miss the
job runs the full generation as before, copies the generated inputs into
the cache directory and saves the entry.

Every key names everything that can change the generated inputs: the
scanned project's commit (the external checkouts are pinned to full commit
SHAs in the workflow), the runner OS and architecture, the cdxgen and atom
versions resolved in a step before the restore, and a `hashFiles` hash of
the dep-scan files that build the cdxgen command line and its environment
(`packages/xbom-lib/src/xbom_lib/cdxgen.py`,
`packages/xbom-lib/src/xbom_lib/process.py`, `depscan/lib/bom.py`,
`depscan/lib/pipeline.py`, `depscan/lib/config.py`, `depscan/cli_options.py`
and `depscan/commands/scan.py`). The self scan's key replaces the project
commit with a hash of `uv.lock` and every `pyproject.toml`, so an ordinary
code change reuses the slices. Each saved entry's size is logged with
`du -sk` into the job log, because the sizes can only be measured where the
generation runs.

A full generation still runs regularly so the cdxgen and atom path itself
keeps being tested: the weekly schedule (Mondays 05:00 UTC) and the
`regenerate` input of the `workflow_dispatch` event both skip the restore
steps. The scheduled or dispatched run must happen on the default branch,
because a pull request can only restore caches its own branch or the
default branch saved; that run is what seeds the entries pull requests
restore. The workflow has no `push` trigger on purpose. A pull request that
misses, for example because it changed a file the key hashes, runs the full
path and saves an entry only that pull request can reuse.

## Adding a project

Add an entry to `projects.json` with the name, Git URL, full commit SHA to
pin, project types and cdxgen arguments, leaving `minReachablePurls` at 0
and `mustReach` empty. Run `generate.sh NAME src/NAME out/NAME` (roughly
`CDXGEN_BIN=<cdxgen 13.8> generate.sh ...`), then check the slices by hand:
`mustReach` names are chosen by reading the reachables slices, not by
running the analyzer and copying its output, and `minReachablePurls` is set
a little below the number the first validated generation reaches, so normal
drift in atom does not fail the tests. Then dispatch the
`repotests-data.yml` workflow, which generates and validates on GitHub
runners before anything is published.

## Refreshing a generation

Dispatch `repotests-data.yml` on `master`. Its `generate` job (one matrix
entry per project, `contents: read`, no secrets) clones each pinned commit
and runs cdxgen 13.8; the `validate` job runs every validator check over
the artifacts; the `publish` job (gated on both, `packages: write`) pushes
one OCI artifact per project with `publish.sh`, writes
`testdata.lock.json` into the run artifacts and the job summary, and
changes nothing else. Opening the pull request that updates the lock file
is a human step on purpose: every refresh is reviewed before the tests move
to it.

The publish job generates from the `projects.json` on `master`, so moving a
project to a newer commit, adding one or changing its arguments takes two
pull requests: the first changes `projects.json` (a dispatch on its branch
generates and validates without publishing), and after it merges and
`master` is dispatched, the second updates `testdata.lock.json` and, when
the counts moved, `minReachablePurls` and `mustReach`.

The first generation (November 2026) was not published by the workflow: a
hosted runner was shut down while forgejo's Go analysis ran. Ten projects
were generated with `generate.sh` inside the `ghcr.io/cdxgen/cdxgen:13.8.0`
image and the three C projects natively with the same cdxgen, atom and
plugins versions, because inside the image cdxgen 13.8.0 adds the image's
own `openssl-devel` package to C BOMs and then fails its validation. All
thirteen passed `validate.py assert` and were pushed with `publish.sh` from
a maintainer's workstation. The manifest annotations record the versions
of each.

## Why the producer is split by privilege

cdxgen research generation executes the scanned project's build tooling:
package managers, compilers, setup scripts. The `generate` job therefore
runs with `contents: read` and no secret, so nothing it executes can write
anywhere. The `validate` job runs no project code at all, only dep-scan's
analyzers over the produced files. Only `publish` can write, needs nothing
but `packages: write` on GHCR, runs neither cdxgen nor project code, and
pushes the same workflow artifacts the `validate` job checked; any failed
generation or validation stops the run before it.

## Scope

The first generations cover the files cdxgen produces: BOMs, slices and
OpenAPI documents. The `sbom-postbuild-*` BOMs of the old dataset come from
blint and return with blint 4; the `sbom-container*` BOMs need the
projects' container images and are not served from this store either. The
Hugging Face dataset `AppThreat/ukaina`, which served all of this before,
is left untouched but no longer used.
