# OWASP dep-scan

dep-scan audits the software you ship for what can actually hurt it: known vulnerabilities in your dependencies, malicious packages, unsafe native code, weak binary hardening, risky supply-chain practices and licence limits. You point it at a source repository, a container image, a binary or a package list; it builds an inventory of what is there, matches it against a vulnerability database you hold locally, and grades every finding by whether the dangerous code is really in your product, really called, and really reachable. Everything runs on your machine. Your code never leaves it, and no model is involved in producing a result.

One scan writes one directory that answers three audiences at once. A person reads the console tables or the HTML report. A CI job reads `--format json`, the documented exit codes and the manifest. A coding agent reads the same files through the `depscan mcp` server or the agent plugin. Nobody re-runs anything to see what another audience saw.

## The ideas behind the tool

Three decisions shape everything on this site. Each names what you will see in the output.

**One finding model.** Every result is a finding of one published schema, whether it came from an advisory match, a call-graph analyzer, a binary review or the licence audit. A finding carries its fix, its references, the producer and version that reported it, a fingerprint that survives unrelated edits, and the evidence that backs it. [The finding model](../results/finding-model) shows the shape; `depscan schema finding` prints it.

**Graded by evidence, on four axes.** Every finding is graded on presence (is the vulnerable code in what you ship), reach (can your code reach it), exposure (can untrusted input get there) and barrier (what stands in the way). An axis is filled only from evidence the scan collected, and a rule table turns the axes into a grade that names its rule. [Exploitability](../results/exploitability) explains how a grade is reached.

**Not assessed is not clean.** When an analyzer did not run, hit a budget or lacked data, the affected findings and stages say so with a reason, in the manifest, the report and the coverage view. A missing tool never reads as a clean scan. [Coverage and not assessed](../results/coverage) lists every state and where it shows.

Underneath sits a deliberate division of work: cdxgen builds the inventory and runs the source analyzers, the vulnerability database owns the advisory data, atom, golem, rusi, dosai, kosi and blint own the analysis, and dep-scan owns orchestration, matching, grading and presentation. A tool it needs is checked at startup by `depscan doctor`; a missing one is a reported reason, not an exception in the middle of a scan.
