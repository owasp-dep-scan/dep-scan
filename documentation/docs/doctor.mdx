# Doctor

`depscan doctor` reports, as text or JSON, every tool a scan may call, where each tool was found, the state of the vulnerability database and, for every capability, whether it can run on the machine where the command stands. It answers the question that comes before any debugging: what can a scan actually rely on here?

The command never prompts, never downloads anything and never writes to the vulnerability database. A missing tool or a missing database is a reported state, not an error: the command exits 0 whenever it produced a report, so a CI job can run it on any runner and attach what it finds.

## The command

```bash
depscan doctor               # text for people
depscan doctor --format json # JSON for scripts and agents
```

Each tool's version comes from the tool itself: its own version option under a ten-second timeout for the commands dep-scan runs, the installed Python distribution for blint, the running interpreter for python, and the manifest the plugins package writes for the binaries cdxgen invokes. Nothing else is ever run. The report is also available from Python through `depscan.api.doctor()`, which returns the same data as the command prints.

## The JSON document

`depscan doctor --format json` prints the same report as one document, which validates against the published `depscan-doctor` schema (`analysis_lib.findings.schemas.validate("depscan-doctor", document)` checks one). The top level carries `schemaVersion`, `depscanVersion`, `platform`, `tools`, `data` and `capabilities`.

| Field | What it holds |
| --- | --- |
| `platform` | `os`, `arch` and, on Linux, `libc` (`glibc` or `musl`), which decides the cdxgen plugin binary token. |
| `tools` | One entry per tool: `name`, the `path` found or null, the `version` or null, the `source` (`path`, `env` with `sourceEnv` naming the variable, `cdxgen-install`, `plugins-dir`, `bundled-sea`, `bundled-runtime`, `library`, `runtime`), and a `reason` when the tool is missing or unusable. cdxgen also carries `minVersion`; plugin binaries carry `platform`. |
| `data.vulnerabilityDatabase` | `present`, `directory`, the `image` and `flavor` recorded by the download marker, `shards` (`enabled` and which are `present`), `createdUtc`, `ageHours`, `stale` against `maxAgeHours`, the `cveDataCount` and `cveIndexCount` row counts, and whether the `extendedMetadataPresent` tables are populated with their `cveMetadataRows` count. |
| `capabilities` | One entry per capability: `name`, `status` (`available`, `unavailable` with the `missing` requirements named, or `not-implemented`), `requirements`, `plan` and `description`. |

## The capability table

One table in the code (`CAPABILITIES` in `depscan/lib/doctor.py`) is the only place that knows which capability needs which tool or data; the report evaluates it against what the machine has. A capability whose analysis this dep-scan version does not contain yet carries no requirements, only the plan section that designs it.
