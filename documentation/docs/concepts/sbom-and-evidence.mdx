# The SBOM, evidence, and cdxgen

## Learning objective

After this chapter you will understand why an accurate, evidence-bearing CycloneDX SBOM is the prerequisite for trustworthy reachability, which cdxgen features produce the evidence dep-scan consumes, and how to recognize a BOM that is too thin to support reachability so you can fix it before scanning.

## Why the BOM is the foundation

dep-scan's reachability engine is purl-keyed and evidence-driven. It needs two things from the BOM that a bare manifest scan will not provide: versioned package URLs for every dependency, and evidence that records where each dependency appears in code. When either is missing, the engine degrades gracefully but visibly: occurrences vanish so `direct_purls` is empty, or purls are versionless so the slicer cannot reconcile a flow onto a BOM component. The symptom is usually a slice file that exists but carries no usable `purls`, which is the most common cause of "no reachable flows were identified." The reachability pipeline is only as good as the BOM that feeds it, which is why this chapter comes before the language guides.

## cdxgen and the analyzer reports

cdxgen is the SBOM generator dep-scan bundles with. Under its research BOM profile (`--bom-profile research` on `depscan scan`, which dep-scan selects itself when reachability is on), cdxgen runs its evinse layer, which drives the per-language analyzers and persists their reports alongside the BOM. The files you will see in the reports directory include atom's `deps`, `usages`, `data-flow` and `reachables` slices, named per language (for example `java-reachables.slices.json`), and the `*-semantics.slices.json` files that carry the raw rusi, golem and dosai reports when cdxgen ran those tools. kosi is the exception: cdxgen does not persist a kosi report, so dep-scan runs kosi itself for Kotlin and Android projects and keeps its report as `analysis/kosi/kosi.json`, and dep-scan likewise runs rusi, golem or dosai itself, with the report under `analysis/<tool>/`, when cdxgen left no report. Each producer's adapter reads its own report into the scan's evidence store (`evidence.jsonl`), and the reachability engine counts the reached purls from that store. The BOM's own evidence is collected the same way and whatever the reachability setting: cdxgen's adapter reads each scanned BOM document's occurrences, callstacks and annotations, and the build-introspection report beside it. The presence axis of the exploitability assessment reads the occurrence and callstack records for the packages whose evidence the package loader keeps: those of a source scan with the default FrameworkReachability analyzer or with reachability off, and those of a single BOM file scanned as the target. A scan that builds its package list from a directory of BOMs grades presence without these records, because the aggregated loader keeps only the identity evidence of each component. That covers a BOM directory scan and every lifecycle scan, including dep-scan's `deep` and `research` profiles (`--profile`), whose SemanticReachability analyzer switches the scan to the lifecycle load; `--bom-profile research` with the default analyzer keeps the records in the grading. A BOM file scanned as the target of a lifecycle scan from outside the aggregated directory keeps its usage evidence. blint's binary review (the reports under `analysis/blint/`) and a trace BOM the scan directory holds (tracebom) are recorded there too, as presence and runtime-trace records; when the scan requested the review, the binary checks also become the binary-hardening findings of `depscan.findings.json`. For most project types the research BOM profile is sufficient; for some, notably Docker images and OS packages, `--deep` is what persuades cdxgen to dig into the layers that carry the real dependencies.

```text
  cdxgen --profile research
     ├─▶ sbom-<type>.cdx.json      component.purl + evidence.occurrences  ─┐
     └─▶ evinse analyzers                                                  │
            ├─▶ *-reachables.slices.json   (atom's own slices) ────────────┤
            └─▶ *-semantics.slices.json    (raw rusi/golem/dosai report) ──┤
  dep-scan runs kosi (and any tool cdxgen did not run)                     │
            └─▶ analysis/<tool>/           (raw kosi report, fallback runs) ┤
  the BOM's own evidence, the binary review, any trace BOM                 │
            └─▶ cdxgen, blint, tracebom adapters (inventory records)      ┤
                                                                           ▼
                              producer adapters (evidence records, purls reconciled)
                                                                           ▼
                                    evidence.jsonl ──▶ reachability engine (reachability.py)
                                                        direct_purls  +  reached_purls
```

## The three pieces of evidence that matter

Three CycloneDX evidence constructs drive the engine, and learning to spot them in a BOM makes reachability debugging straightforward.

The purl (`component.purl`) is the join key for everything. It must be versioned (for example `pkg:cargo/time@0.1.45`, not `pkg:cargo/time`) because the vulnerability feed and the analyzers' output both key on the versioned purl. Native analyzers often emit versionless purls, which is why each adapter has a reconciler that maps by name onto the BOM's versioned purls. A BOM whose components lack versions will silently break reachability even when the analyzer reports are perfect.

`component.evidence.occurrences` records where a dependency appears in code. Each occurrence carries a location (typically a file path), and cdxgen populates it from real imports, requires, and using directives. The engine builds `direct_purls` from these occurrences, so a component with occurrences is "imported in source" while a component without them is "merely declared in a manifest." cdxgen's evidence adapter also records each occurrence and callstack in the evidence store, which is what the presence axis of the exploitability assessment reads on the scans described above (BOM directory and lifecycle scans grade presence without them). This is the distinction that lets dep-scan separate a dependency that is wired into the application from one that is transitively pulled but never referenced.

`component.evidence.callstack.frames` is the richer, call-stack form of evidence that some project types emit. When present, it gives the engine a structured path from an entry point to the component, which is what the semantic analyzer uses to attribute endpoint and service reachability. Not every project type produces callstack frames, and that is acceptable: FrameworkReachability works from occurrences alone.

## Recognizing and fixing a thin BOM

A reachability-hostile BOM has recognizable symptoms. The analyzer reports are empty or very small (`java-reachables.slices.json` for atom, the `*-semantics.slices.json` file for the native tools), which means the analyzer found no flows to trace. The reports carry flows but the evidence store's records hold no purls, which usually means the BOM lacked the occurrence and purl information needed for the adapter to attribute a flow to a component. Or the components in the BOM have no `evidence` block at all, which tells you cdxgen ran without the research profile or the deep option.

The fixes follow from the causes. Run with cdxgen's research BOM profile (`--bom-profile research`) so cdxgen persists slices and evidence, and add `--deep` for image and OS-package scans. Make sure the source tree is in the state cdxgen expects for the language: a restored .NET tree (so `project.assets.json` and `*.deps.json` are present), a built Java tree with resolved Maven or Gradle dependencies, a Go module cache warm enough for golem to load packages, or a Cargo.lock that resolves real versions. The language chapters call out the per-language prerequisite in each case. When a large project produces no slices at all, the cause is often resource exhaustion during slicing, which is covered in the troubleshooting notes of the [Framework reachability](../analyzers/framework-reachability) chapter.

## Summary

Reachability is evidence-driven, and the evidence comes from cdxgen. The three things to verify before chasing a reachability problem are that components carry versioned purls, that those components have `evidence.occurrences`, and that the analyzer reports are non-trivial. With those in place, the engine and every language guide behave predictably. From here, the natural next step is the guide for your language under Language Guides, or the [Framework reachability](../analyzers/framework-reachability) chapter for the analyzer internals.
