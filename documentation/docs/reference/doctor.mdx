# Doctor

`depscan doctor` reports, as text or JSON, every tool a scan may call, where each tool was found, the state of the vulnerability database and, for every capability, whether it can run on the machine where the command stands. It answers the question that comes before any debugging: what can a scan actually rely on here?

The command never prompts, never downloads anything and never writes to the vulnerability database. A missing tool or a missing database is a reported state, not an error: the command exits 0 whenever it produced a report, so a CI job can run it on any runner and attach what it finds. To make a missing capability fail the command instead, name it with `--require`.

Every scan collects this report once and records the tools, the platform and the evaluated capability table in its manifest, and the analysis steps consult the same capability table when a tool they need is missing. That is why the manifest of a scan where an analyzer was missing names the capability and the doctor's reason; see [the scan directory](../results/scan-directory).

## The command

```bash
depscan doctor               # text for people
depscan doctor --format json # JSON for scripts and agents
depscan doctor --require vulnerabilities,reachability:go
```

`--require` takes capability names, comma-separated or repeated. The command still prints the report, then exits with code 4 when any named capability is not available on the machine, whether a requirement is missing or the capability is not implemented in this version. An unknown capability name exits with code 2 before anything is checked. A container image build can use this to fail when the image lacks a capability it is meant to have.

Each tool's version comes from the tool itself: its own version option under a ten-second timeout for the commands dep-scan runs, the installed Python distribution for blint, the running interpreter for python, and the manifest the plugins package writes for the binaries cdxgen invokes. Nothing else is ever run. The report is also available from Python through `depscan.api.doctor()`, which returns the same data as the command prints.

A tool whose version could not be read is reported as `version unknown` and stays usable, with two exceptions that follow the checks a scan makes. A scan refuses a cdxgen without a readable version or older than 13.8.0, and it skips Go or .NET analysis when `go version` or `dotnet --version` fails, so the report marks those tools unusable in the same cases. rusi has a soft minimum: an older rusi is reported with a note and stays usable, because a scan only warns. A tool that dep-scan does not use yet, edga for example, is still listed so the capability table can name it.

## The JSON document

`depscan doctor --format json` prints the same report as one document, which validates against the published `depscan-doctor` schema (`analysis_lib.findings.schemas.validate("depscan-doctor", document)` checks one). The top level carries `schemaVersion`, `depscanVersion`, `platform`, `tools`, `data` and `capabilities`.

| Field | What it holds |
| --- | --- |
| `platform` | `os`, `arch` and, on Linux, `libc` (`glibc` or `musl`), which decides the cdxgen plugin binary token. |
| `tools` | One entry per tool: `name`, the `path` found or null, the `version` or null, the `source` (`path`, `env` with `sourceEnv` naming the variable, `cdxgen-install`, `plugins-dir`, `bundled-sea`, `bundled-runtime`, `library`, `runtime`), and a `reason` when the tool is missing or unusable. cdxgen and rusi also carry `minVersion`; plugin binaries carry `platform`. |
| `data.vulnerabilityDatabase` | `present`, `directory`, the `image` and `flavor` recorded by the download marker, `shards` (`enabled` and which are `present`), `createdUtc`, `ageHours`, `stale` against `maxAgeHours`, the `cveDataCount` and `cveIndexCount` row counts, and whether the `extendedMetadataPresent` tables are populated with their `cveMetadataRows` count. |
| `capabilities` | One entry per capability: `name`, `status` (`available`, `unavailable` with the `missing` requirements named, or `not-implemented`), `requirements`, the dep-scan `issue` that designs or tracks it, and `description`. |

## The capability table

One table in the code (`CAPABILITIES` in `depscan/lib/doctor.py`) is the only place that knows which capability needs which tool or data; the report evaluates it against what the machine has. A capability whose analysis this dep-scan version does not contain yet carries no requirements, only the issue that designs it.
