# The dep-scan command line

This page is the reference for the verbs, their options and the sections of behaviour a reader needs to look up: what each target kind means, what each check runs, how the JSON output is shaped and the rest. The pages under Start and Scan your software explain the same options as part of a task; here they are the whole truth in one place.

## The verbs

The dep-scan 7 command line starts with a verb: `depscan scan`, `depscan vdb`, `depscan serve` and so on. Each verb owns its options, and `depscan <verb> --help` prints them.

| Verb | What it does |
| --- | --- |
| `scan` | Scan a project, BOM, purl or container image for vulnerabilities. |
| `report` | Render the console tables and explanations of a saved scan. |
| `vdb` | Download and inspect the vdb vulnerability database. |
| `doctor` | Report the tools, data and capabilities a scan can use here. |
| `schema` | Print the published finding schemas. |
| `config` | Show the effective scan options or write a config file. |
| `serve` | Run depscan as a server. |
| `mcp` | Run the MCP server over stdio for agents and MCP clients. |
| `validate` | Validate CSAF VEX or CycloneDX VDR/VEX documents against their schema. |
| `version` | Print the dep-scan version, with tool versions as JSON. |
| `help` | Show the top-level help, or one verb's help. |

The table rows are the verbs' own help descriptions. The two blocks below are the parsers' own help output, printed at a fixed terminal width (`COLUMNS=200 uv run depscan --help` and `COLUMNS=200 uv run depscan scan --help`); a test regenerates them from the built parsers, so they cannot drift:

Fully open-source security and license audit for application dependencies and container images based on known vulnerabilities and advisories.

  {scan,report,vdb,doctor,schema,config,serve,mcp,validate,version,help}

## Exit codes

The table is generated from the exit-code constant in `depscan/commands/output.py`, and a test keeps the page in step with it:

<!-- exit code table start -->
| Code | Meaning |
| --- | --- |
| 0 | Success. |
| 1 | A scan or command that could not run, for example an unusable vulnerability database or a source target that does not exist. |
| 2 | A usage error, including any dep-scan 6 command line. |
| 4 | A requested capability that cannot run, for example a named check whose analyzer is missing, or an iOS or firmware target. |
<!-- exit code table end -->

Findings never change the exit code in this version: a scan that reports vulnerabilities still exits 0, and a clean scan never exits non-zero for being clean. When a verb in json format stops with a failure that ends it as a whole, stdout carries the error document; a scan whose targets fail and a validate with invalid documents keep their own documents and exit 1. A caller can parse stdout as one JSON document whatever the exit code.

## Target detection

The scan verb takes what to scan as positional targets, and detects each target's kind: a source directory, git URL, container image reference or archive, BOM file, BOM directory, purl, binary or app package.

| Kind | Detected as | What the scan uses |
| --- | --- | --- |
| `purl` | a string starting with `pkg:` | the purl search |
| `git` | a git URL (`http://`, `https://`, `git://`, `ssh://` or `git@`) that does not end in an archive extension | the remote source |
| `container` | a string that is not an existing path and has the shape of an image reference (`name:tag`, `registry/name[:tag]` with lowercase path components, or `name@sha256:<digest>`), a `.tar` or `.tar.gz` archive file, or a directory holding an `oci-layout` file | the container image |
| `bom` | an existing JSON file whose document is a CycloneDX BOM | that BOM |
| `bom-dir` | an existing directory whose JSON files are all CycloneDX documents, not counting the `*.slices.json` reachability slices and dep-scan's own `depscan.manifest.json` and `depscan.findings.json` | every BOM in the directory |
| `binary` | an existing file that starts with an ELF, PE or Mach-O header | blint binary analysis |
| `android` | an existing `.apk` or `.aab` file | blint app analysis |
| `ios` | an existing `.ipa` file | refused (see below) |
| `source` | an existing path no more specific kind names, or any other string | the source tree |

An existing path beats a same-shaped image reference: a string that is both a possible image reference and an existing path is scanned as the path, whatever kind the path itself gives.

`--target-kind KIND` forces the kind of every target instead of detecting it. `ios` and `firmware` have no inventory path in this version: naming either (or scanning a `.ipa` file) stops the scan with exit 4 and the reason on stderr. A `source` target that does not exist is refused with exit 1, and so is an `http://` or `https://` URL to an archive file, which dep-scan does not download. A path such as `./app`, `/srv/app` or `~/app` is never read as an image reference. A directory that holds other JSON files next to its BOMs is detected as a source directory; pass `--target-kind bom-dir` for it. Detection logs, on stderr, the kind chosen for each target and the evidence behind it.

When the user passed no `-t`, the kind names the project type too: a `container` target scans as `docker`, a `binary` target as `binary` and an `android` target as `apk`.

## The checks

`--checks` takes a comma-separated list of check names: `all`, `vulnerabilities`, `reachability`, `license`, `supply-chain`, `binary`, `memory-safety`, `mobile`, `code`, `crypto`.

| Check | What it maps onto | Capability gate |
| --- | --- | --- |
| `vulnerabilities` | vulnerability matching, including the malware advisory reporting | none: always assessed |
| `reachability` | keeps the reachability analyzers on | `reachability` |
| `license` | appends the `license` pseudo type, which triggers the license analysis | `license` |
| `supply-chain` | the supply-chain audit through cdxgen's `cdx-audit` (cdxgen 13.10.0 or newer) | `supply-chain` (needs `cdx-audit`) |
| `binary` | adds the `binary-analysis` technique: a binary or apk target is scanned through blint's own BOM, a source target keeps its cdxgen inventory with blint's security review running beside it, and a container target today gives the review no units to attempt | `binary` (needs the blint package) |
| `memory-safety` | not implemented in this version | exits 4 when named explicitly |
| `mobile` | not implemented in this version | exits 4 when named explicitly |
| `code` | not implemented in this version | exits 4 when named explicitly |
| `crypto` | not implemented in this version | exits 4 when named explicitly |

An explicit `--checks` list defines the whole optional set: checks not named are off, so `--checks vulnerabilities` turns reachability off. The `vulnerabilities` check always runs, named or not. A check named explicitly whose capability cannot run on the machine stops the scan with exit 4 before any work, printing the doctor's reason on stderr. `--checks all` selects every check whose capability is available, turns the unavailable ones off, and records each of them in the manifest as a `check-<name>` stage with status `not-assessed` and the doctor's reason. A scan whose every target is a BOM file or BOM directory produces no BOM, so neither the gate nor `all` holds a missing cdxgen or language plugin (golem, rusi, dosai, kosi, and the Go and .NET runtimes) against it: reachability reads the slices beside the BOMs, and an analyzer with no slices there is recorded as not assessed.

Without `--checks` and without `--profile` the set is `vulnerabilities,reachability`, and it is never gated.

The binary check on a source scan never replaces the scan's own inventory: the cdxgen BOM keeps every source component and its vulnerability findings, and blint's review reports land under `analysis/blint/` with each review result in `depscan.findings.json` as a `binary-hardening` finding. A review that fails is recorded as a failed `binary-review` stage on the manifest, with blint's reason.

## The profiles

`--profile` names one of five scan profiles. Each sets a check set and analyzer settings; an explicitly passed option always wins over the profile, so `--profile quick --reachability-analyzer FrameworkReachability` keeps framework reachability on.

| Profile | Checks | Other settings |
| --- | --- | --- |
| `quick` | `vulnerabilities` | reachability off |
| `ci` | `vulnerabilities,reachability` | explanations off, so no LLM prompt file is ever written |
| `deep` | `vulnerabilities,reachability,license,supply-chain` | semantic reachability (`SemanticReachability`) |
| `research` | `deep` plus cdxgen's research BOM profile | `--bom-profile research` implied |
| `offline` | `vulnerabilities,reachability` | no database download, local cdxgen only, golem offline, no supply-chain audit |

## BOM profiles and excluded types

`--bom-profile` is cdxgen's own BOM profile flag (`appsec`, `research`, `operational`, `threat-modeling`, `license-compliance` and the machine-learning profiles), the option v6 called `--profile`. It shapes the BOM cdxgen generates; the v7 `--profile` (above) shapes the scan instead.

`--exclude-type` drops a project type from the detected list before any stage runs, so no inventory or scan runs for it: excluding `os` or `docker` stops the OS and container scans. The type is also passed to cdxgen as a repeated `--exclude-type` argument, so the BOM contents are filtered the same way. The option is repeatable and accepts comma-separated values.

```bash
depscan scan . --exclude-type os --exclude-type docker
```

## Excluding trees from a scan

A source scan reads the whole tree it is given, test fixtures and build material included, so a tree such as `test/` can add components and findings that are not part of the product. Name the trees to leave out with `--exclude` patterns in `--cdxgen-args` (or the `CDXGEN_ARGS` environment variable):

```bash
depscan scan /absolute/path/to/project --cdxgen-args "--exclude 'test/**' --exclude 'ci/**'" -o /absolute/path/to/reports
```

The patterns follow cdxgen's rules. They are globs anchored at the scanned path, never at the working directory, and `*` matches one path segment. `test/**` leaves out the `test` directory at the scanned root only; a leading `**/` is needed only to reach same-named directories nested below the root. Quote each pattern so the shell does not expand it, and give one `--exclude` per tree.

dep-scan reads the same patterns once and applies them to every walk it starts itself, so a tree that is excluded for cdxgen is excluded everywhere: the targets of blint's binary review and of the post-build BOM, and the targets of the golem, rusi, kosi and dosai runs dep-scan makes when cdxgen left no report. dosai, and a blint that accepts an exclusion parameter, receive the patterns. blint is always handed only the directories and files the patterns keep. golem, rusi and kosi analyse one project directory per run and take no exclusion argument, so dep-scan starts each on the one project root the patterns leave (a scan path that is itself a project stays the target). When the patterns remove every project of that language, or remove some of several projects so that more than one remains, no run starts: the tool's reachability is reported as not assessed with that reason, and the fix is to scan one project directory or to exclude none of them. A scan whose patterns leave blint nothing to inventory fails with a reason saying so. No separate option exists for this. Excluding `test/**` from a scan of a tree that keeps `.nupkg` fixtures there removes their NuGet components, the vulnerability findings on them and the binary-hardening findings blint reported for them.

A source scan of a tree that holds Dockerfiles or compose files also reads every image those files name. cdxgen pulls the images the local daemon lacks and extracts their layers, whatever the scan type, so a tree whose container files are build or CI material turns a scan into a long image-pulling run whose result depends on the daemon's state. Look for container files before scanning a large tree, and exclude the folders that hold CI or build images (for example `--exclude 'ci/**' --exclude 'contrib/**'`) when they are not product content. Container files under an excluded tree add no image pulls. A scan that outruns cdxgen's time budget fails with a reason naming the budget; `CDXGEN_TIMEOUT_MS` raises it (see [the environment variables](configuration)).

## JSON output

`--format json` selects the output on every verb: the verb writes exactly one JSON document on stdout, followed by a newline, and nothing else on stdout, whatever the exit code. The banner is suppressed, and the tables, progress and logs move to stderr, so `depscan scan . --format json | jq` sees exactly the document. A failing verb also prints its message on stderr as one plain text line.

The scan verb prints `{"scans": [...]}`, one entry per given target, also for a single target and for zero targets. A scanned entry carries `target`, `kind`, `scanDir`, `manifest` and `findings`; a target the detection refused gets `{"target", "kind": null, "error"}` with the reason, so no target is silently dropped. When a verb stops with a failure that ends it as a whole, stdout carries the error document `{"error": {"exitCode", "verb", "message", "details"}}` instead; per-target failures do not, so a scan with a refused target and a validate with an invalid document keep their own documents and exit 1. Every verb's document has a published JSON Schema, and `depscan schema` lists the names. The full contract, the per-verb documents and one runnable example per verb are on [the agents page](../integrate/agents).

```bash
depscan scan . --format json
```

## Several targets

Passing more than one target runs one scan per target, each writing into `<reports-dir>/<n>-<name>/`, where `n` is the target's 1-based position and `<name>` its basename for an existing path, or the reference with `/`, `\`, `:` and `@` replaced by `-`, for a purl, URL or image reference; every name is truncated to 60 characters, and a name that comes out empty becomes `target`. The exit code is the highest of the scans.

```bash
depscan scan app/src app/bom.json --reports-dir reports
```

Zero or one target uses `--reports-dir` as given.

## dep-scan 6 command lines are refused

A command line that starts with an option, as every dep-scan 6 invocation did, is not run. dep-scan translates it, prints the equivalent v7 command and a link to the migration guide on stderr, and exits 2.

```text
$ depscan --src .
depscan: this is a dep-scan 6 command line, which dep-scan 7 no longer runs.
The equivalent v7 command is: depscan scan .
See the migration guide: https://depscan.readthedocs.io/upgrade/migrate-v6-to-v7/
```

Bare `depscan` is a usage error too; use `depscan scan` to scan the current directory. `depscan -h` and `depscan --help` still print the help and exit 0.

## Scanning container images

Scan an image reference, a digest reference, or an archive saved with `docker save`:

```bash
depscan scan shiftleft/scan-slim -o containertests
depscan scan redmine@sha256:a5c5f8a64a0d9a436a0a6941bc3fb156be0c89996add834fe33b66ebeed2439e -o containertests
docker save -o /tmp/scanslim.tar shiftleft/scan-slim:latest
# podman save --format oci-archive -o /tmp/scanslim.tar shiftleft/scan-slim:latest
depscan scan /tmp/scanslim.tar -o reports
```

The container target is detected from the reference shape, so `-t docker` is not needed. [The container images page](../targets/container-images) explains what an image scan reads and what it cannot see.

## Specify the BOM engine

The supported values of `--bom-engine` are `auto`, `CdxgenGenerator`, `CdxgenServerGenerator`, `CdxgenImageBasedGenerator` and `BlintGenerator`:

- **auto**: Uses the cdxgen server (`CdxgenServerGenerator`) when `--cdxgen-server` is passed, and the local cdxgen CLI (`CdxgenGenerator`) for a container image, OS or hardware project type (`docker`, `podman`, `oci`, `os` or `hardware`). For every other project it takes the first of these that applies: the cdxgen bundled inside the standalone dep-scan executable; the local cdxgen CLI when `CDXGEN_CMD` is set or a cdxgen found on the machine meets the minimum version; the cdxgen container image (`CdxgenImageBasedGenerator`) when the Docker command (`DOCKER_CMD`, `docker` by default) is on `PATH` and the platform is not Windows; and otherwise the local cdxgen CLI. A local cdxgen below the minimum version is refused with the command that installs a supported one.
- **CdxgenGenerator**: Always uses the local cdxgen CLI. Install cdxgen using the npm command or download the standalone executable.
- **CdxgenServerGenerator**: Uses the cdxgen server. Specify the URL using the `--cdxgen-server` argument.
- **CdxgenImageBasedGenerator**: Generates a BOM using the official cdxgen container images. You can customize the image name using `CDXGEN_IMAGE_{project_type}` and `CDXGEN_IMAGE_VERSION`. Container image-based generation is more suitable for enterprise applications that require specific build tools and OS libraries for successful BOM generation. This approach is resource-intensive but typically has a higher success rate.
- **BlintGenerator**: Uses the OWASP [blint](https://github.com/owasp-dep-scan/blint) library for post-build and binary inventories. This requires the `ext` extra:

    ```bash
    pip install owasp-depscan[ext]
    ```

### Customize the cdxgen container image

Container images used by `CdxgenImageBasedGenerator` can be customized using environment variables prefixed with `CDXGEN_IMAGE_`. For example, to use a custom cdxgen image for Java, set the environment variable `CDXGEN_IMAGE_JAVA`.

## Specify the vulnerability analyzer

The supported values of `--vulnerability-analyzer` are `auto`, `VDRAnalyzer` and `LifecycleAnalyzer`:

- **auto**: Uses LifecycleAnalyzer when the target is a BOM directory containing multiple xBOMs; otherwise, it defaults to VDRAnalyzer.
- **VDRAnalyzer**: Matches the vulnerabilities of a single BOM and a single lifecycle phase.
- **LifecycleAnalyzer**: Generates and analyses BOMs for several lifecycle phases (pre-build, build, post-build) by repeatedly invoking cdxgen (and blint for post-build), which is what the lifecycle and semantic reachability workflows read. Use the environment variable `DEPSCAN_SOURCE_IMAGE` to specify the image for container BOM generation, and `DEPSCAN_BUILD_DIR` for the build output directory.

## Configuration file

Scan options persist in a configuration file. By default, depscan reads the file the `DEPSCAN_CONFIG` environment variable names, or `.config/depscan.toml` in the current directory when the variable is unset, and `depscan scan --config <path>` names another file for one scan. A sample file named `depscan.toml.sample` is generated in the reports directory on every scan. Copy the sample into `.config/` to run depscan without repeating the arguments.

`depscan config show` prints every scan option with its value and where the value came from (the command line, `depscan.toml`, an environment variable or the default), and `depscan config init` writes the effective options to the same default file (`$DEPSCAN_CONFIG`, or `.config/depscan.toml`, creating `.config/` when needed), refusing to overwrite one that exists. The file holds flat keys matching the long option names (`vdb_flavor = "app-only"`, `reachability_analyzer = "SemanticReachability"`); [the configuration page](configuration) lists the details and the environment variables.

## The other verbs

```bash
# Run dep-scan as a server (the --server-* options live here; there is no --config on serve)
depscan serve --server-host 127.0.0.1 --server-port 7070

# Download or inspect the vulnerability database
depscan vdb download --flavor app-only

# Show every scan option with its value and where it came from

```

`depscan doctor` reports the tools, database and capabilities a scan can use on this machine, and `depscan report` re-renders a saved scan directory. Both have their own pages: [depscan doctor](doctor) and [the scan directory](../results/scan-directory).

## Vulnerability database management (depscan vdb)

The `depscan vdb` command selects, downloads, and inspects any published vdb flavor or shard set. See [the vulnerability database page](../start/vulnerability-database) for the full flavor matrix.

```bash
# Default full (app+OS) flavor
depscan vdb download

# Smaller app-only flavor
depscan vdb download --flavor app-only

# Extended flavor (for severity and metadata search)
depscan vdb download --flavor app-extended

# Type shards for a scoped workload
depscan vdb download --shards pypi npm
```

`depscan vdb info` prints the local database and shard store state, and `depscan vdb path` prints the `VDB_HOME` directory. The deprecated `--scope`/`--time`/`--extended` aliases still work on `download` with a warning naming the flavor they resolve to. There is no per-distro database on the v7 line; `--distro` is rejected with the flavors listed.

## Suggest mode

Suggest mode is on by default and retrieves the optimal fix version for each vulnerability from the sources, so the fix version in the report is sometimes a later version than the first patched one, chosen to avoid landing on another known vulnerability. The optimal fix version may still not be the right version for your application; read it as a suggestion. Pass `--no-suggest` to disable the behaviour.

## The supply-chain audit

`--checks supply-chain` runs cdxgen's `cdx-audit` over the BOM the scan produced or was given, in its direct BOM audit mode. The findings it reports become dep-scan's `supply-chain` findings, with cdxgen's rule ids, severities and the components each finding names; the audit's raw report lands in the scan directory as `cdx-audit-<type>.json`, and the per-finding evidence goes into `evidence.jsonl` with `cdx-audit` as the producer. Source and BOM scans audit the `package-integrity` and `dependency-source` rule packs; a BOM that carries Cargo crates adds `cargo-security`, and container scans (the `docker`, `image`, `oci`, `container`, `podman`, `rootfs` and `oci-dir` types, or a BOM whose root component is a container) add `container-risk`, `rootfs-hardening` and `cbom-security` to those packs. A container scan's `cbom-security` findings are `crypto` findings and its `rootfs-hardening` findings `binary-hardening` findings, all with `cdx-audit` as their producer. A BOM directory scan audits every BOM in the directory, with one `cdx-audit-bom-<path>.json` report per BOM named from its relative path (a JSON file that is no CycloneDX document, such as cdxgen's introspection report, is skipped), and a lifecycle scan audits the documents each project type produced. The scan prints the findings as a Supply-Chain Audit Results table, which `--no-vuln-table` leaves out, and `depscan report` prints the same table from a saved scan directory.

Before the rules run, the audit looks the BOM's npm, PyPI and Cargo components up in their registries, one request per package, because for dependencies only the registry states whether a version is deprecated or yanked, whether it exists at all, and how old the package is. Whatever the audit could not assess is stated, never folded into a clean result: a target its predictive mode skipped or failed, a target cap or time budget that cut its queue, a registry lookup that did not run, and each component no registry answered for. Each of these is a coverage reason on every finding of that audit and a not-assessed reason on the manifest's `risk` stage, and the last two are stated even when the audit found nothing.

The `deep` and `research` profiles add cdx-audit's predictive mode, which resolves the required dependencies to their upstream repositories, generates child SBOMs and audits those under a target cap of 25 and a 30-minute budget that hold for each project type in total: every BOM's run gets what the earlier runs left, and a BOM that finds either bound spent is not run, which the manifest's `risk` stage states. It runs only for a BOM that holds npm, PyPI or Cargo packages, the ecosystems it selects targets from. A predictive run that fails leaves the direct audit's findings in place and becomes a coverage gap with one warning; a failed direct run marks the `risk` stage failed. The `offline` profile passes `--offline`, so the audit makes no registry, git or OCI request at all; the registry rules then assess none of the scan's packages, and the manifest says so.

The two profiles imply the supply-chain check without naming it. On a machine whose `cdx-audit` is missing or older than the minimum they record the check as a not-assessed `check-supply-chain` entry in the manifest, the way `--checks all` records the checks it cannot run, print one warning and run the rest of the profile; `--checks supply-chain` on the same machine exits 4. A purl scan with neither `--checks` nor `--profile` runs the audit too; a purl scan that names its checks runs exactly those.

Malicious-package matching (`MAL-` advisories) stays in the matching stage, from the vulnerability database.

Dependency confusion: use `--private-ns` to name the private package namespaces or name prefixes your organisation registers. Every package whose name starts with one of them is looked up on the public npm registry, the Python Package Index or crates.io, whichever can hold it, with one request per name. A name the public registry holds is a finding from cdx-audit's INT-017 to INT-019 rules, for npm scopes and for PyPI and Cargo names. A private package that resolves from your own index and is not published publicly is the intended state and is not reported. Prefixes match by prefix, so `appthreat` matches both the npm scope `@appthreat` and a PyPI name that starts with `appthreat`. The check needs the network: under the `offline` profile the public registry is not asked, so the check assesses none of the matching packages, and the manifest's `risk` stage says so.

```bash
depscan scan . --checks supply-chain --private-ns appthreat,shiftleft
```

The rules that replace the retired registry audit: install-time scripts (INT-001); a deprecated npm package, where the version in use or the newest release is deprecated (INT-005); a yanked Cargo crate (INT-010) or PyPI release (INT-030); a version the registry does not list (INT-020 to INT-022); a package first published inside the one-year quarantine window (INT-023 to INT-025); a package whose newest release is more than six years old (INT-026 to INT-028); and an npm version that ships or builds native code, by an `os`, `cpu` or `libc` constraint, a node-gyp build, or the host it downloads a prebuilt binary from (INT-029). A `bin` entry does not count: it names a script the package runs. Each rule carries its own severity; the rule catalogue lives in cdxgen's `data/rules/` directory and is documented in cdxgen's BOM audit guide. cdxgen 13.10.0 or newer is required, because the audit passes it `--private-namespace`, `--fetch-registry-metadata`, `--offline` and `--time-budget-minutes`; `depscan doctor` reports the installed one as the `cdx-audit` tool, found through `CDX_AUDIT_CMD`, then on `PATH`, then beside the cdxgen install. To run against a development build of cdxgen that already carries those options, set `CDX_AUDIT_CMD` to its `cdx-audit` and `DEPSCAN_CDX_AUDIT_MIN_VERSION` to its version; the doctor then reports that version as the minimum.

## Custom reports

dep-scan renders a [Jinja](https://jinja.palletsprojects.com/en/3.1.x/) template with `--report-template` and writes the result with `--report-name`. A starter template is generated in the reports directory, and the repository ships examples under `contrib/report-templates`:

```jinja
{% if metadata -%}
Report for {{ metadata.component.group }}:{{ metadata.component.name }}:{{ metadata.component.version }}
{% endif -%}

{% if vulnerabilities -%}
There were {{ vulnerabilities | length }} issues identified:

{% for vuln in vulnerabilities -%}
* {{ vuln['bom-ref'] }} - {{ vuln.recommendation }}
{% endfor -%}
{% else -%}
_No vulnerabilities found_
{% endif -%}

Severity counts:
* Low: {{ summary.LOW }}
* Medium: {{ summary.MEDIUM }}
* High: {{ summary.HIGH }}
* Critical: {{ summary.CRITICAL }}
* Unspecified: {{ summary.UNSPECIFIED }}
```

The objects available to the template come from the CycloneDX `.vdr.json` the scan wrote: `metadata`, `vulnerabilities`, `components`, `dependencies` and `services`, plus `summary` (severity counts), `pkg_vulnerabilities` (the same vulnerabilities from the VDR) and `pkg_group_rows` (vulnerability id and dependency tree pairs).

## Custom vulnerability data

A directory of local vulnerability data can override and augment the downloaded database at runtime: add internal advisories that are not public, or mark specific versions unaffected where the public data is wrong for your use. Custom data follows the **CVE 5.2 JSON Schema**, in `.json`, `.yaml`, `.yml` or `.toml` files, named by `--custom-data`:

```bash
depscan scan pkg:npm/my-lib@1.0.0 --custom-data /path/to/custom/vulns
depscan serve --custom-data /path/to/custom/vulns
```

A new vulnerability record uses the `cna` container. If a CVE id and package URL combination exists in the custom data, vdb uses it instead of the entry from the official database, which is how a false positive is corrected: append or dispute through an **ADP** container, marking the specific version `unaffected`. Where two records disagree, the custom data wins; the rest of the database is untouched.
