# Lesson 6: a supply-chain and licence audit

This lesson runs the supply-chain and licence checks over the same pinned Juice Shop commit as lesson 1 and reads the files they write. The supply-chain check runs cdxgen's `cdx-audit` over the scan's BOM, so its findings carry cdxgen's rule ids, severities and the components each one names; the licence check writes its report beside them. Both write plain JSON into the scan directory, so the audit is a file a reviewer opens, not console output to scrape.

The inputs are pinned: Juice Shop at commit `33518f5a0911`, the `app-only` database flavor, and the cdxgen release the supply-chain check needs (13.9.0 or newer, which ships `cdx-audit` with the options dep-scan passes). The output below is from a run on 2026-11-26 with dep-scan 7.0.0a3 and the cdxgen 13.9.0 master build that already carries the audit options; the lesson's CI job installs the cdxgen release instead.

As in lesson 1, the commit pins the source but not the dependency tree: Juice Shop at this commit ships no lockfile (its `.npmrc` sets `package-lock=false`), so the dependencies are resolved at scan time and the counts below can drift between runs. The install writes `node_modules` and a `package-lock.json` into the clone, which is acceptable for the throwaway clone the script makes.

## The script

The commands live in `documentation/lessons/06-supply-chain-licence/run.sh` (and `expect.txt` beside it holds the output lines the lesson's CI job greps for). The page embeds the script verbatim, so the page and the script cannot differ:

```bash
#!/usr/bin/env bash
# Lesson 06: a supply-chain and licence audit.
#
# Runs the supply-chain and licence checks over the same pinned Juice Shop
# commit as lesson 01, and reads the supply-chain findings, the audit's own
# report, the licence report and the manifest stages that record what ran.
#
# Needs: dep-scan, cdxgen 13.9.0 or newer (for the cdx-audit it ships),
# Node.js, and an app-only vulnerability database.
set -euo pipefail

WORK="${WORK:-/tmp/depscan-lesson-06}"
SRC="$WORK/juice-shop"
SCANS="$WORK/scans"
COMMIT=33518f5a0911e25d9df747b1e70fb7af279a755c
mkdir -p "$SCANS"

### Pin the project
if [ ! -d "$SRC/.git" ]; then
  git clone --quiet https://github.com/juice-shop/juice-shop.git "$SRC"
fi
git -C "$SRC" checkout --quiet $COMMIT
echo "project: juice-shop $COMMIT"

### Run the supply-chain and licence checks
depscan scan "$SRC" --checks supply-chain,license --vdb-flavor app-only --no-banner \
  --cdxgen-args "--exclude 'Dockerfile' --exclude 'docker-compose*.yml'" \
  -o "$SCANS/reports"

### What ran, in the manifest's own words
python3 - "$SCANS/reports" <<'PY'
import json, sys
d = sys.argv[1]
m = json.load(open(f"{d}/depscan.manifest.json"))
for s in m["stages"]:
    if s["name"] in ("licenses", "risk"):
        print(f"stage {s['name']}: {s['status']}")
PY

### Read the supply-chain findings
python3 - "$SCANS/reports" <<'PY'
import json, sys
d = sys.argv[1]
findings = json.load(open(f"{d}/depscan.findings.json"))["findings"]
supply = [f for f in findings if f["category"] == "supply-chain"]
print(f"supply-chain findings: {len(supply)}")
rules = {}
for f in supply:
    rules[f["rule"]] = rules.get(f["rule"], 0) + 1
top = sorted(rules.items(), key=lambda kv: (-kv[1], kv[0]))[:3]
print("most frequent rules: " + ", ".join(f"{rule} x{n}" for rule, n in top))
if supply:
    producer = supply[0]["producer"]
    print(f"producer: {producer['name']} {producer['version']}")
audit = json.load(open(f"{d}/cdx-audit-universal.json"))
mode = audit.get("auditMode", "predictive")
print(f"audit mode: {mode}, total findings: {audit['summary']['totalFindings']}")
PY

### Read the licence report
python3 - "$SCANS/reports" <<'PY'
import json, sys
d = sys.argv[1]
rows = json.load(open(f"{d}/license-universal.json"))
print(f"licence rows: {len(rows)}")
copyleft = [r for r in rows if "Same License" in r.get("License conditions", "")]
print(f"copyleft conditions flagged: {len(copyleft)}")
PY
```

## Reading the run

The manifest names the two stages the checks add, beside the matching every scan does, and the script then reads what they wrote:

```text
project: juice-shop 33518f5a0911e25d9df747b1e70fb7af279a755c
stage licenses: completed
stage risk: completed
supply-chain findings: 533
most frequent rules: INT-026 x306, INT-029 x148, INT-005 x24
producer: cdx-audit 13.9.0
audit mode: direct, total findings: 504
licence rows: 5
copyleft conditions flagged: 2
```

The supply-chain findings are not a scored package list: each one is a rule match with cdxgen's rule id, the severity cdx-audit gave it and the component it names. On the recorded run, INT-026 (a package whose newest release is more than six years old) matched 306 times, INT-029 (an npm version that ships or builds native code: a platform constraint, a node-gyp build, a node-pre-gyp binary, or the platform packages a package ships through, which is how rollup and esbuild publish theirs) 148, INT-005 (an npm version in use that is deprecated) 24, INT-031 (an npm package whose newest release is deprecated) 21, and INT-001 (install-time execution hooks) and INT-023 (a package first published inside the one-year quarantine window) 17 each. The audit's own report, `cdx-audit-universal.json`, holds 504 findings, and the two counts differ for two reasons. Juice Shop installs its server and its Angular frontend separately, so a package both trees pin is declared by `package-lock.json` and by `frontend/package-lock.json`, and each lockfile's copy is its own finding (324 and 209 findings name those two files), so suppressing one does not silence the other. Within one lockfile, a package resolved at two versions is one finding whose components name both purls, because a finding's fingerprint keys on the package (17 findings name more than one version); all 485 components the audit named stay named. The audit first looked all 1844 registry-resolvable components up in their registries and every one was answered; its coverage block says so, and a run that could not look a component up says that instead. Every finding names its producer (`cdx-audit` and the cdxgen version that ran), so a reader knows which audit answered. The console prints the same findings as the Supply-Chain Audit Results table, which `depscan.txt` and `depscan.html` carry too.

Read the rule ids, not the counts: the dep-scan 6 risk audit flagged 382 packages on this project against a weighted score, and the supply-chain findings replace that list with one finding per rule and component. A private namespace (`--private-ns appthreat,shiftleft`) turns on the dependency-confusion check: each matching package name is looked up on its public registry, and one the public registry holds is reported by INT-017 to INT-019. Under the `deep` or `research` profiles the check adds cdx-audit's predictive mode, which audits the upstream repositories of the required dependencies; a target it skips or fails is counted in the findings' coverage reasons, never folded into clean.

The licence report is deliberately small on this project: five rows resolved to licence ids with conditions, two of them copyleft. Packages whose BOM carries no licence data are counted on the manifest's licenses stage as not assessed rather than silently clean (282 of 2137 packages on the recorded run). A licence policy gate (allowed and denied lists in the config, violations as findings) is planned work; today the file is the audit, read the way you would read a spreadsheet.

## Takeaways

- `--checks supply-chain,license` adds two stages, the audit report `cdx-audit-<type>.json` and the plain JSON reports to the scan directory.
- Supply-chain findings are rule matches with cdxgen's rule ids and severities, one per rule and component; read the rule, not a score.
- Missing licence data is counted as not assessed on the manifest, never folded into clean.
