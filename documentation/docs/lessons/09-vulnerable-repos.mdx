# Lesson 9: deliberately vulnerable projects

This lesson scans three well-known intentionally vulnerable applications at pinned commits and reads what dep-scan proves on each, and what it cannot. The three cover different ecosystems: Juice Shop (Node), DVWA (PHP) and railsgoat (Ruby). npm is a reachability ecosystem with atom behind it; PHP and Ruby are matched-only today, and the reports say so.

The inputs are pinned: Juice Shop at `33518f5a0911`, DVWA at `068d974487a2`, railsgoat at `f5951f13089d`, and the `app-only` database flavor. The output below is from a run on 2026-11-25 with dep-scan 7.0.0a3, cdxgen 13.9.0 from its master branch and atom 4.0.3; the lesson's CI job installs the cdxgen 13.8.0 release instead. The scans are typed (`-t js`, `-t php`, `-t ruby`) so the container files in these trees do not turn a source scan into an image pull.

Juice Shop at this commit ships no lockfile (its `.npmrc` sets `package-lock=false`), so its dependencies are resolved at scan time and its finding count can drift between runs, as in lessons 1 and 6. The install writes `node_modules` and a `package-lock.json` into the clone, which is acceptable for the throwaway clones the script makes.

## The script

The commands live in `documentation/lessons/09-vulnerable-repos/run.sh` (and `expect.txt` beside it holds the output lines the lesson's CI job greps for). The page embeds the script verbatim, so the page and the script cannot differ:

```bash
#!/usr/bin/env bash
# Lesson 09: what dep-scan proves on deliberately vulnerable projects, and
# what it cannot.
#
# Scans three well-known vulnerable applications at pinned commits: Juice
# Shop (Node), DVWA (PHP) and railsgoat (Ruby), and reads the findings and
# the reach verdicts: npm is a reachability ecosystem, PHP and Ruby are not,
# and the reports say so instead of implying it.
#
# Needs: dep-scan, cdxgen, Node.js, PHP and Ruby for their managers, and an
# app-only vulnerability database.
set -euo pipefail

WORK="${WORK:-/tmp/depscan-lesson-09}"
SCANS="$WORK/scans"
mkdir -p "$SCANS"

### Pin the three projects
clone() {
  local url="$1" commit="$2" dir="$3"
  if [ ! -d "$WORK/$dir/.git" ]; then
    git clone --quiet "$url" "$WORK/$dir"
  fi
  git -C "$WORK/$dir" checkout --quiet "$commit"
}
clone https://github.com/juice-shop/juice-shop.git 33518f5a0911e25d9df747b1e70fb7af279a755c juice-shop
clone https://github.com/digininja/DVWA.git 068d974487a297c155c48722f9fcf7180a83adc4 DVWA
clone https://github.com/OWASP/railsgoat.git f5951f13089d85c979de09e7da3c8c0fb982f94a railsgoat
echo "pinned: juice-shop, DVWA, railsgoat"

### Scan each project typed
# Typed scans keep the container files in these trees from turning a source
# scan into an image-pulling run.
depscan scan "$WORK/juice-shop" -t js --bom-profile research --vdb-flavor app-only \
  --no-banner \
  --cdxgen-args "--exclude 'Dockerfile' --exclude 'docker-compose*.yml'" \
  -o "$SCANS/juice-shop"
depscan scan "$WORK/DVWA" -t php --vdb-flavor app-only --no-banner -o "$SCANS/dvwa"
depscan scan "$WORK/railsgoat" -t ruby --vdb-flavor app-only --no-banner \
  -o "$SCANS/railsgoat"

### What v7 proves, and what it cannot
# A project whose findings carry no reach verdict gets the reason from its
# manifest: the enrichment stage lists each reachability analyzer the scan
# could have used, and a not-assessed analyzer carries the reason it gave.
python3 - "$SCANS" <<'PY'
import json, sys
scans = sys.argv[1]
for name in ("juice-shop", "dvwa", "railsgoat"):
    f = json.load(open(f"{scans}/{name}/depscan.findings.json"))
    reaches = {x.get("exploitability", {}).get("axes", {}).get("reach") for x in f["findings"]}
    assessed = all(r in ("likely", "proven", "unknown") for r in reaches)
    print(f"{name}: reach assessed: {assessed}, findings {len(f['findings'])}")
    if assessed:
        continue
    m = json.load(open(f"{scans}/{name}/depscan.manifest.json"))
    gaps = [a for s in m["stages"] for a in s.get("analyzers", [])
            if a["status"] != "completed"]
    for a in gaps:
        print(f"{name}: reach verdict is not_assessed; manifest: "
              f"{a['name']} {a['status']}: {a.get('reason', 'no reason given')}")
    if not gaps:
        print(f"{name}: reach verdict is not_assessed; the manifest lists no analyzer for it")
PY
```

## Reading the run

One line per project says what v7 proves and where it stops, and for the projects without a reach verdict the script reads the reason from the scan's manifest:

```text
pinned: juice-shop, DVWA, railsgoat
juice-shop: reach assessed: True, findings 93
dvwa: reach assessed: False, findings 1
dvwa: reach verdict is not_assessed; manifest: atom not-assessed: no atom report was given; the adapter has nothing to read
railsgoat: reach assessed: False, findings 258
railsgoat: reach verdict is not_assessed; manifest: atom not-assessed: no atom report was given; the adapter has nothing to read
```

The contrast is the lesson. On Juice Shop, 93 advisory matches and an analyzer behind them: 11 reached, 82 assessed and not reached, and the reached ones carry witness paths. On railsgoat, 258 advisory matches (the bundled Rails stack), each correct as a version match, and none with a reach verdict, because no reachability analyzer produced a report for the scan. On DVWA, one finding: the project's PHP is scanned from its composer manifest, and most of the application is not composed packages at all, which is a real limitation of manifest-based scanning on non-package-managed code, not a defect of the match.

The script takes the gap from each manifest's enrichment stage, which lists every reachability analyzer the scan could have used. For the PHP and Ruby scans that list is atom alone, since no language-specific analyzer covers either type, and atom's entry reads `not-assessed` with its adapter's reason: no atom report was given, so there was nothing to read. The findings of those two projects carry `reach` in their `unassessed` list. Their prioritization leans on severity, exploit evidence and the fail-safe rules instead of a traced path. That is the honest answer to "which of these 258 first": severity and insight order them, and only an ecosystem with an analyzer can prove the rest.

## Takeaways

- Reachability is per ecosystem: proved where an analyzer covers the language, `not_assessed` where none does.
- A manifest-based scan of an application that is not managed by a package manager inventories little; DVWA's one finding is the honest size of that inventory.
- Intentionally vulnerable projects make good negative and positive controls; the corpus behind the release uses them the same way.
