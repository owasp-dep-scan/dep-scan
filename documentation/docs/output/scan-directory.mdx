# The scan directory

Every dep-scan scan writes one directory: the reports directory named by `-o`/`--reports-dir` or `DEPSCAN_REPORTS_DIR`, `reports` under the current directory by default. One case reuses a directory that already exists: when the scan's only target is a single BOM directory and no `-o`, `--reports-dir` or `DEPSCAN_REPORTS_DIR` was given, that BOM directory is the reports directory, so the manifest, the findings file and the VDR land next to the BOMs and `depscan report` loads the directory. An explicit reports directory, or more than one target, keeps the usual behaviour (more than one target writes `<reports-dir>/<n>-<name>/` per target); a BOM directory scanned with an explicit reports directory has its VDR written next to the BOMs, outside the scan directory, and that reports directory is refused at load time (see below). The BOM and VDR files keep the names and places they have always had, and cdxgen's slice files stay where cdxgen puts them, so existing scripts and CI jobs keep reading them. On top of those, the scan writes four files of its own, `depscan.manifest.json`, `depscan.findings.json`, `evidence.jsonl` and `evidence.index.json`, and keeps the raw reports of the tools it runs itself under `analysis/`. A saved directory is all `depscan report` reads, and the layout version in the manifest decides whether an older or newer dep-scan reads it.

## The layout

```text
reports/
├── depscan.manifest.json          the manifest, written last of every file
├── depscan.findings.json          one finding per advisory and component
├── evidence.jsonl                 the evidence store, one record per line
├── evidence.index.json            record ids by component purl and finding
├── sbom-python.cdx.json           the BOM documents, named as before
├── depscan-universal.vdr.json     the VDR files, named as before
├── python-reachables.slices.json  the slice files cdxgen writes: atom's own
│                                  slices and the semantics reports (a
│                                  <language>-reachables file an earlier
│                                  dep-scan wrote may linger in a reused
│                                  directory)
├── analysis/
│   ├── rusi/rusi.json             raw reports of the tools dep-scan runs itself
│   ├── golem/golem.json
│   ├── dosai/dotnet-methods.json, dotnet-dataflows.json
│   ├── blint/findings.json        the binary review's reports: findings.json,
│   │                               reviews.json and analysis-coverage.json
│   └── tracebom/                  a trace BOM the scan directory holds
├── license-python.json            the license and risk reports
├── depscan-risk-python.json
├── depscan.html, depscan.txt      the rendered reports
└── report.csaf.json               the CSAF VEX document, with --csaf
```

The tree shows every kind of file a scan can write; a scan writes only the ones that apply to it. A package URL target has no BOM, so its scan writes no BOM and no VDR, and its findings are in `depscan.findings.json` alone.

Raw reports that cdxgen writes itself, such as the `<type>-semantics.slices.json` files cdxgen persists for the language analyzers and the atom slice files, stay where cdxgen puts them; the manifest lists them where they are. A BOM the user passed as a BOM file or BOM directory target is never moved.

## The role of each file

The manifest's `files` array carries one entry for every file at the top of the directory and under `analysis/`, except the manifest itself. Other subdirectories are not listed, because the reports directory can be a user's BOM directory or sit inside the scanned project. Each entry has the path relative to the directory (always with forward slashes), a `role`, the `producer`, the `projectType` when the file name carries one, and the SHA-256 digest of the bytes.

| Role | Files | Written by |
| --- | --- | --- |
| `bom` | `sbom-<type>.cdx.json` and its lifecycle siblings, and a BOM the user placed here | cdxgen, blint (post-build), or `user` |
| `vdr` | `*.vdr.json`, including `depscan-universal.vdr.json` | dep-scan |
| `findings` | `depscan.findings.json` | dep-scan |
| `evidence` | `evidence.jsonl`, `evidence.index.json` | dep-scan |
| `slices` | `*.slices.json`, the slice files cdxgen writes: atom's own slices and the semantics reports | cdxgen, or dep-scan for the converted reachables slices its earlier versions wrote |
| `raw-report` | everything under `analysis/<producer>/` | the tool named by the directory: a reachability plugin, blint's binary review, or tracebom |
| `csaf` | `*.csaf.json` | dep-scan |
| `report` | `depscan.html`, `depscan.txt`, `depscan-prompts.md`, the license and risk reports, `depscan.toml.sample` and the template report | dep-scan |
| `other` | everything else, for example `*-openapi.json` | varies |

## The findings file

`depscan.findings.json` holds `schemaVersion` and a `findings` array. Every entry in the array is one finding of the published `depscan-finding` schema: one per advisory and component, with the fingerprint as its `id`, the advisory id as its `rule`, the most severe rating, the versions named as fixes, and `producer` set to dep-scan and its version. A scan that requested blint's binary review also writes the review's binary-hardening findings, built from the blint evidence records the scan collected, with the blint version the blint-written BOM names as their producer version. When the review's coverage report counts failed or skipped units, each binary-hardening finding lists those `coverage-gap` caveats among the reasons of its `coverage` block, so a partial review never reads as a complete one. A scan that found no vulnerabilities writes the file with an empty array, so an assessed-empty scan is distinguishable from a directory nobody scanned.

## The manifest

The manifest records what the scan read and what ran, so a directory can be interpreted without re-running anything: the inputs with their digests, the tools and capabilities of the machine as `depscan doctor` saw them, the database flavor and shards the matching stage used, the stages with their status, and the options with secrets removed. Two properties are worth knowing before reading one:

- It is written last, after every other file, through a temporary file and a rename. A manifest that lists files lists files that exist, and an interrupted scan never leaves a half-written manifest behind.
- The enrichment stage lists the reachability analyzers the scan could have used. An analyzer is `completed` when its evidence adapter read a report of that analyzer: the scan ran the tool, cdxgen persisted its report, or a BOM directory scan was given one under a name the adapter looks for. Otherwise it is `not-assessed` with the adapter's reason: what was wrong with the report it found, or, when it found none, the doctor's reason naming the capability when the tool or toolchain is missing on this machine, and otherwise the report names it looked for. A BOM directory scan reads the reports the directory holds whether or not the tool is installed, so a damaged report is named as damaged on any machine. The doctor's reason stands in only when no adapter ran. An installed tool is never reported as an analysis that ran.
- No absolute path, username or hostname appears outside the `inputs` array, which records each path as the user gave it. Paths in `files` are relative. The tool paths come from the doctor report with the user's home replaced by `~`, and options that can hold a secret, such as `cdxgen_args` or `vdb_image`, are recorded as `"<redacted>"` when they were set and null when they were not.

### Manifest fields

| Field | What it holds |
| --- | --- |
| `layoutVersion` | The scan directory layout version as major.minor. Layout 2.0 introduced the evidence store. A reader accepts any minor version of a major it knows and refuses any other major. |
| `depscanVersion` | The version of dep-scan that ran the scan. |
| `startUtc` | When the scan started, in UTC, as an RFC 3339 date-time. |
| `endUtc` | When the scan ended, in UTC, as an RFC 3339 date-time. A scan that stopped early still records its end. |
| `inputs` | Every source directory, BOM file, BOM directory and package URL the scan read. Paths are recorded as the user gave them, so this is the only place an absolute path, a username or a hostname may appear. |
| `tools` | The doctor report's tool entries, collected once for this scan. |
| `platform` | The doctor report's platform entry: os, arch and, on Linux, libc. |
| `capabilities` | The doctor report's evaluated capability table, collected once for this scan. |
| `database` | The doctor report's database inspection, plus the flavor and shards the matching stage actually used. |
| `stages` | One entry per stage, in the order the stages ran. A stage that stopped the scan is recorded as failed with its reason; the stages after it are absent. |
| `options` | The parsed scan options. Options whose name can hold a secret are recorded as the string "<redacted>" when they were set, and path-valued options are recorded in inputs instead, so no absolute path appears here. |
| `files` | Every file at the top of the scan directory and under analysis/, except the manifest itself. Other subdirectories are not listed. Paths are relative to the directory, always with forward slashes. |

## The version rule

`layoutVersion` is a `major.minor` string. Layout 2.0 introduced the evidence store. A reader accepts any minor version of a major it knows: layout `2.3` loads with dep-scan that writes `2.0`, because a minor bump adds optional things, and a manifest whose major is 1 predates the evidence store and is refused. A different major is refused with an error naming both versions, the one in the manifest and the one the reader supports.

## Loading a directory back

`depscan.api.load_scan(reports_dir)` and `depscan report` both read the manifest when it is present: the project types, the files and the stage results come from the manifest, the vulnerabilities from the VDR files it lists, and the findings from `depscan.findings.json`. A project type that found no vulnerabilities loads as an empty result, because the manifest shows its matching stage completed. A type whose matching was skipped or failed is listed in `project_types` but gets no result, a manifest in which no matching stage completed is refused rather than loading as clean, and so is a BOM directory scan given a separate `--reports-dir`, whose VDR is written next to the BOMs outside the scan directory, and a directory without a manifest is still read the way scans before the scan directory wrote them: the VDR files are recognised by name, and a clean scan's directory cannot be loaded at all, because such a scan wrote no VDR.

## depscan report

```bash
depscan report <scan-dir>
depscan report <scan-dir> --explain --explanation-mode EndpointsAndReachables
```

`depscan report` re-renders a saved directory: the results table and the summary counts of every project type, and with `--explain` the explanation the scan rendered, reading the evidence store and the OpenAPI specifications the directory holds. It never generates BOMs, never runs analyzers and never opens the vulnerability database. A directory that cannot be loaded, or an explanation whose inputs the directory does not hold, is answered with the reason on stderr and exit code 1.

## The evidence files

`evidence.jsonl` is the scan's evidence store: one record per line, sorted by id, each record a `depscan-evidence` schema object saying what one producer observed. The reachability producers (atom, rusi, golem, kosi, dosai) contribute the reached flows, usages, entry points, exploit chains, sanitizers and negative findings such as dead code that the reachability engine counts. Three evidence producers contribute records without grading reachability. cdxgen's adapter reads every BOM document the scan loaded, whatever the reachability setting: each component's `evidence.occurrences` and `evidence.callstack`, the document-level `annotations`, and the build-introspection report that sits beside the BOM. It gates each document on the cdxgen version its `metadata.tools` names: versions 10.0 through 13.9 are read as they are, a newer 13.x minor version adds a `schema-minor` caveat to every occurrence, callstack, annotation and entry-point record of the BOM (the introspection record carries only its own report's gate caveats), version 14 or later leaves the document not assessed, and a version older than 10.0, or a BOM whose tools name no cdxgen version, gives records with a `schema-unknown` caveat. When the adapter leaves a document not assessed, every loaded package that document's components name carries the adapter's reason in the `coverage` of its findings, under the `presence:usage` capability with reason `report-not-assessed`, even when another assessed BOM's records proved presence: the reason names the BOM file that was not read. A package no assessed BOM gave usage records, and that no reach analyzer reached, keeps the grade the database match and the component scope give it (`likely`, or `unlikely` for an optional or excluded component). The occurrence records of the BOM's top-level components are also the direct uses the reachability engine counts as `direct_purls`, one per occurrence entry; occurrences of nested components prove presence but are not counted as direct uses. The occurrence and callstack records are the usage evidence the presence axis of the exploitability assessment reads, on every scan type, from every BOM the scan read and the adapter assessed, for the components the scan loaded: a record whose component names a `bom-ref` grades when that ref is a loaded component's key (the `bom-ref`, else the purl), and a record whose component has no bom-ref grades when one of its purls matches a loaded component's purl compared percent-decoded, without qualifiers or subpath, and case-insensitively for nuget, which is how a record from any BOM of an aggregated directory reaches the aggregated component. That covers source scans, a single BOM file scanned as the target, BOM directory scans and every lifecycle scan, which `--vulnerability-analyzer LifecycleAnalyzer`, `--reachability-analyzer SemanticReachability` and the `deep` and `research` profiles select (a lifecycle source scan aggregates the BOMs it writes to the reports directory). Records of components the loader left out (a `data` component, a nested `application`, a component of a BOM the scan did not load) grade nothing; the matching stage's manifest entry counts them in its `notAssessed` line, in the form "N cdxgen usage records grade nothing: their components are not in the loaded package list". The records are written to the store in every mode. blint's adapter reads the binary review's findings, capability reviews and coverage report (`findings.json`, `reviews.json` and `analysis-coverage.json` under `analysis/blint/` beside the BOM), when the scan requested the review or a BOM directory scan found the reports there; the coverage report's failed and skipped units become `coverage-gap` caveats on every blint record. dep-scan never runs tracebom, so trace BOMs are input the user supplies with a BOM directory scan: tracebom's adapter reads the trace BOMs under `analysis/tracebom/` in that directory and any trace-shaped JSON at its top level, never the reports directory, and gates each one on the cdxgen version its `metadata.tools` names (12.6, the first release that ships tracebom, through 13.9), since tracebom ships inside the cdxgen package. Its `runtime-trace` records never count as reached, because a traced run observes the libraries, endpoints and algorithms of the traced command, whose purls do not in general match the scanned BOM's components, and a library loaded at run time shows no code path from the application to it. cdxgen's, blint's and tracebom's adapters run right after each project type's inventory stage, and the enrichment stage writes the store once the reachability adapters have read their reports; a type scanned with reachability off still writes a store, holding the inventory records and no reachability ones. A type that stops before enrichment (a blint-written BOM listing no components, for example) writes the store from its inventory records, so its binary-hardening findings and records survive. A store or index an earlier scan left in the reports directory is removed when the scan starts, in every scan mode, so a scan that collected no records has no store at all rather than an earlier scan's records. The records carry the producer's own words: a record's `confidence` is the one the producer stated, exactly as stated, and is absent when the producer stated none; witness paths are the producer's own; and nothing is inferred from advisory text. Where an adapter must decide something the producer left open, the record says so: a dosai entry without a confidence is counted by its kind's default, which the record names in the attributes `confidenceSource: "kind-default"` and `confidenceDefault` without setting `confidence`. The caveats are the producer's statements (a budget or timeout it hit, call sites it could not resolve) plus the ones the adapter adds about its reading: `schema-minor` and `schema-unknown` for the report's schema version, `minimal-api` for dosai attribution the producer can get wrong, `location-outside-root` when a file the producer named lies outside the source root and outside every package directory the adapter can spell (a file in a package cache such as the Go module cache, the Cargo registry or the NuGet cache is spelled by its package and version, as in `github.com/example/lib@v1.0.0/lib.go`), so the record leaves it out, and `record-skipped` on the analyzer's result, counting per reason the report objects that became no record.

`evidence.index.json` maps the records to what they are about: `byComponent` maps each component purl to the ids of the records whose subject includes it, and `byFinding` maps each finding fingerprint to the ids of the records that touch the finding's component. It is written once the findings exist, before the manifest lists both files with their digests.
