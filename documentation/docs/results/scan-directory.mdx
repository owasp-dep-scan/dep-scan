# The scan directory

Every scan writes one directory, and everything that reads a scan afterwards reads only that directory: `depscan report`, the MCP server, the Python API and any script. The directory is self-describing. Its manifest records what the scan read, which tools ran, which did not and why, so a scan directory can be interpreted, filtered or diffed without re-running anything, on another machine, months later.

The directory is the reports directory named by `-o`/`--reports-dir` or `DEPSCAN_REPORTS_DIR`, `reports` under the current directory by default. One case reuses an existing directory: when the scan's only target is a single BOM directory and no reports directory was named, that BOM directory is the reports directory, so the manifest, the findings file and the VDR land next to the BOMs. Several targets write `<reports-dir>/<n>-<name>/` per target. With a reports directory named, nothing is written into the BOM directory: the VDR, the manifest and every other output go to the reports directory.

The VDR is named `depscan-universal.vdr.json` whether the scan read the universal BOM (`sbom-universal.cdx.json`, which the default profile and `--profile research` both write) or a BOM directory. A scan of any other BOM writes `<bom>.vdr.json` beside it, for example `sbom-docker.vdr.json`. Scan directories written before this naming was unified hold `sbom-universal.vdr.json` instead; `depscan report` and `depscan.api.load_scan` read either name.

## The layout

```text
reports/
├── depscan.manifest.json          the manifest, written last of every file
├── depscan.findings.json          one finding per advisory and component
├── evidence.jsonl                 the evidence store, one record per line
├── evidence.index.json            record ids by component purl and by finding
├── sbom-python.cdx.json           the BOM documents, named as before
├── depscan-universal.vdr.json     the VDR, one per universal BOM or BOM directory
├── python-reachables.slices.json  the slice files cdxgen writes
├── analysis/
│   ├── rusi/rusi.json             raw reports of the tools dep-scan runs itself
│   ├── golem/golem.json
│   ├── dosai/dotnet-methods.json, dotnet-dataflows.json
│   ├── blint/findings.json        the binary review's reports
│   └── tracebom/                  a trace BOM the scan directory holds
├── license-python.json            the license report
├── cdx-audit-python.json          the supply-chain audit report
├── depscan.html, depscan.txt      the rendered reports
└── report.csaf.json               the CSAF VEX document, with --csaf
    csaf.toml.sample               the starter CSAF metadata, with --csaf
```

A scan writes only the files that apply to it: a package URL target has no BOM, so its scan writes no BOM and no VDR, and its findings are in `depscan.findings.json` alone. Files that scripts already read keep the names and places they have always had: the BOM and VDR files, and cdxgen's slice files, are untouched by the scan directory layout. The manifest's `files` array carries one entry for every file at the top of the directory and under `analysis/`, with its path relative to the directory (always forward slashes), a `role`, the producer, and the SHA-256 digest of the bytes, so a copied directory can be checked file by file.

| Role | Files | Written by |
| --- | --- | --- |
| `bom` | `sbom-<type>.cdx.json` and its lifecycle siblings, and a BOM the user placed here | cdxgen, or blint for any BOM blint wrote; `user` for a BOM the user placed here |
| `vdr` | `*.vdr.json`, including `depscan-universal.vdr.json` | dep-scan |
| `findings` | `depscan.findings.json` | dep-scan |
| `evidence` | `evidence.jsonl`, `evidence.index.json` | dep-scan |
| `slices` | `*.slices.json` | cdxgen |
| `raw-report` | everything under `analysis/<producer>/` | the tool named by the directory |
| `csaf` | `*.csaf.json` | dep-scan |
| `report` | `depscan.html`, `depscan.txt`, the license report, the `cdx-audit-<type>.json` audit reports, the sample toml files, a template report | dep-scan |
| `other` | everything else, for example `*-openapi.json` | varies |

## The findings file

`depscan.findings.json` holds `schemaVersion` and a `findings` array, one finding per advisory and component of [the finding model](finding-model). The same file carries the binary-hardening findings of the blint review, with blint as their producer, and each carries the review's coverage gaps among its coverage reasons, so a partial review never reads as a complete one. A scan that requested the supply-chain check also writes the cdx-audit findings, one per cdx-audit rule and component, with cdxgen's rule id as the rule and `cdx-audit` with the cdxgen version that ran as the producer. A scan that assessed everything and found nothing writes the file with an empty array; a scan in which nothing at all was assessed writes no findings file at all, and its manifest shows why ([coverage](coverage)).

## The supply-chain audit report

`cdx-audit-<type>.json` is the JSON report cdxgen's `cdx-audit` wrote for this project type's BOM, exactly as the tool wrote it, and `cdx-audit-predictive-<type>.json` is its predictive run when the profile asked for one. A type with several BOMs (a BOM directory scan, a lifecycle scan) gets one report per BOM, named `cdx-audit-<type>-<bom name>.json`, and a purl scan's audit input is `cdx-audit-input-<type>.json`. No scan of the directory reads a `cdx-audit-` file back as a BOM. The audit's findings become `supply-chain` findings in `depscan.findings.json` (a `cbom-security` rule becomes a `crypto` finding and a `rootfs-hardening` rule a `binary-hardening` finding), with cdxgen's rule id as the rule, cdx-audit's severity, and the producer named `cdx-audit` with the cdxgen version that ran. The per-finding evidence is in `evidence.jsonl` as `annotation` records. Whatever the audit could not assess becomes a `coverage-gap` caveat on the records and in every finding's `coverage` reasons, and is listed on the manifest's `risk` stage as a `notAssessed` reason, so a bounded or offline audit never reads as a complete one: a target the predictive audit skipped or failed, a target cap that cut its queue, a spent time budget, a registry lookup that did not run (it does not under the `offline` profile), and each npm, PyPI or Cargo component no registry answered for. The last two are stated even when the audit found nothing, so a scan with no supply-chain finding can still say that its registry rules assessed none of the packages.

## The manifest

The manifest is written last, through a temporary file and a rename, so a directory with a manifest lists files that exist. It holds the inputs with their digests, the doctor report's tools and capabilities, the database flavor and shards used, one entry per stage with its status, the parsed options with secret-valued options redacted, and the `files` array. The tables below are generated from the schema (regenerate with `uv run python -c "from depscan.lib.scan_directory import manifest_fields_markdown; print(manifest_fields_markdown())"` when it changes).

### Manifest fields

| Field | What it holds |
| --- | --- |
| `layoutVersion` | The scan directory layout version as major.minor. Layout 2.0 introduced the evidence store. A reader accepts any minor version of a major it knows and refuses any other major. |
| `depscanVersion` | The version of dep-scan that ran the scan. |
| `startUtc` | When the scan started, in UTC, as an RFC 3339 date-time. |
| `endUtc` | When the scan ended, in UTC, as an RFC 3339 date-time. A scan that stopped early still records its end. |
| `inputs` | Every source directory, BOM file, BOM directory and package URL the scan read. Paths are recorded as the user gave them, so this is the only place an absolute path, a username or a hostname may appear. |
| `tools` | The doctor report's tool entries, collected once for this scan. |
| `platform` | The doctor report's platform entry: os, arch and, on Linux, libc. |
| `capabilities` | The doctor report's evaluated capability table, collected once for this scan. |
| `database` | The doctor report's database inspection, plus the flavor and shards the matching stage actually used. |
| `stages` | One entry per stage, in the order the stages ran. A stage that stopped the scan is recorded as failed with its reason; the stages after it are absent. |
| `options` | The parsed scan options. Options whose name can hold a secret are recorded as the string "&lt;redacted&gt;" when they were set, and path-valued options are recorded in inputs instead, so no absolute path appears here. |
| `files` | Every file at the top of the scan directory and under analysis/, except the manifest itself. Other subdirectories are not listed. Paths are relative to the directory, always with forward slashes. |

One naming detail prevents a common misreading: options are recorded under their internal names, and both `--bom-profile` and `--profile` land on the same key, `profile`. A manifest from a scan run with `--bom-profile research` alone shows `profile: research` although no scan profile was set. Which checks ran is not an options key at all: the stage list is the record, with a `licenses`, `risk` or `explain` stage skipped when a check or explanation was not requested, and a `check-<name>` stage per check `--checks all` had to leave off.

No absolute path, username or hostname appears outside the `inputs` array, which records each path as the user gave it. Tool paths come from the doctor report with the user's home replaced by `~`. Paths are relative; options that can hold a secret are `"<redacted>"`.

## Loading a directory back

`depscan.api.load_scan(reports_dir)` and `depscan report` both read the manifest first: the project types, the files and the stage results come from it, the vulnerabilities from the VDR files it lists, and the findings from the findings file. A project type that found no vulnerabilities loads as an empty result, because the manifest shows its matching stage completed. A type whose matching was skipped or failed is listed but gets no result, a manifest in which no matching stage completed is refused rather than loaded as clean, and a manifest whose layout major this dep-scan does not know is refused with both versions named. A directory without a manifest is still read the way scans before the scan directory wrote them, recognised by the VDR file names; a directory with neither a manifest nor a VDR is refused rather than reported as clean.

The version rule: `layoutVersion` is a `major.minor` string, and a reader accepts any minor version of a major it knows. Layout 2.0 introduced the evidence store; a manifest whose major is 1 predates it and is refused with an error naming both versions.

## `depscan report`

```bash
depscan report reports
depscan report reports --explain --explanation-mode EndpointsAndReachables
```

`depscan report` re-renders a saved directory: the results table and the summary counts of every project type, and with `--explain` the explanation the scan rendered, reading the evidence store and the OpenAPI specifications the directory holds. It never generates BOMs, never runs analyzers and never opens the vulnerability database, so it is fast and safe to run anywhere. A directory that cannot be loaded, or an explanation whose inputs the directory does not hold, is answered with the reason on stderr and exit code 1.
