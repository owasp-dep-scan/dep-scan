# The finding model

Every result dep-scan writes, whatever produced it, is a finding of one shape. An advisory match, a memory-safety defect, a binary-hardening gap, a licence conflict, a malicious package and a project-health note are all findings, in one file, with one schema. That is what makes the rest of the tool uniform: filters, suppressions-ready fingerprints, the MCP server's queries and the policy-shaped questions a CI job asks all work the same way over every category, and adding an analyzer adds findings of the same shape rather than a new report format.

The schema is published. `depscan schema finding` prints it (or `depscan schema` for the list of every published schema), and `depscan.findings.json` in the scan directory holds one finding per entry, validated against it.

## What a finding carries

This is one real finding, from a scan of the requests package at 2.31.0, trimmed to the fields most reads need:

```json
{
  "id": "dsf1:051156050d1997a2cb9f0d66fde02338813c7838215cb72355144d5ffad42828",
  "category": "vulnerability",
  "rule": "CVE-2024-47081",
  "severity": "medium",
  "coverage": { "state": "assessed" },
  "cwes": [522],
  "components": ["pkg:pypi/requests@2.31.0"],
  "exploitability": {
    "axes": { "presence": "likely", "reach": "not_assessed", "exposure": "not_assessed", "barrier": "not_assessed" },
    "grade": "moderate",
    "rule": "assessed"
  },
  "fix": { "fixed_versions": ["2.32.4"] },
  "producer": { "name": "dep-scan", "version": "7.0.0a3" },
  "references": [
    { "url": "https://nvd.nist.gov/vuln/detail/CVE-2024-47081", "type": "advisory" }
  ]
}
```

The fields, and what each is for:

| Field | What it holds |
| --- | --- |
| `id` | The fingerprint: `dsf1:` followed by a SHA-256 digest. It never contains line or column numbers, so baselines and suppression lists survive unrelated edits. |
| `category` | One of `vulnerability`, `malware`, `memory-safety`, `supply-chain`, `binary-hardening`, `mobile`, `code`, `license`, `crypto`, `health`. |
| `rule` | The advisory id or the analyzer rule id that fired: `CVE-2021-23337`, `GHSA-p6mc-m468-83gw`, `MS-BOUND-001`, or the id of a cdxgen audit rule. |
| `title` | A short statement of the finding. It never copies source text or environment values. |
| `severity` | The severity the producer assigned: `critical`, `high`, `medium`, `low`, `info` or `unknown`. |
| `confidence` | How sure the producer is, when it expresses one. |
| `cwes` | The CWE numbers that classify the defect. |
| `components` | The affected components as package URLs, versions included. |
| `locations` | Where the finding applies: file, line, function, or a binary and an offset. Findings without source (a vulnerable package, a hardening gap) point at the manifest or lockfile that declares the component. |
| `coverage` | Whether the analysis that owns this finding ran, and why not when it did not; see [coverage](coverage). |
| `exploitability` | The four axes, the grade, the rule id that produced the grade and the producers that filled each axis; see [exploitability](exploitability). |
| `triage` | Reserved for the human decision about the finding; not written in this version. |
| `fix` | The versions that fix the finding, when the producer knows them. |
| `producer` | The tool and version that produced the finding. A binary-hardening finding names blint and the version the BOM records. |
| `evidence` | Ids into the scan's [evidence store](evidence) that back the finding. |
| `references` | Links to advisories and upstream reports. |
| `properties` | Extension name and value pairs, the way CycloneDX carries them. |

## The fingerprint

Two copies of the same vulnerable package, two versions of one advisory, or a file that moved all produce stable ids: the digest covers the rule id, the component purl without its version, the relative file, the enclosing function and the API names on the evidence path, never the line numbers. The id is what a baseline compares and what `get_finding` on the MCP server takes. Because the version is stripped, one advisory hitting two versions of a package shares one id; the evidence index keys its second level on the component purl, so the two stay distinguishable there.

## Where findings live and who reads them

`depscan.findings.json` is the contract file. The console tables, the HTML report, the CSAF and VDR documents, the MCP server and the Python API all read from it (the VDR keeps only the advisory-shaped findings, as CycloneDX requires). A scan that assessed everything and found nothing writes the file with an empty array, so an assessed-clean scan stays distinguishable from a directory nobody scanned; a scan where nothing at all was assessed writes no findings file, and its manifest shows why.
