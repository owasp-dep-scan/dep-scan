# The agent plugin

dep-scan ships a coding-agent plugin in `agent-plugin/`. It gives an agent the skills to scan projects and container images, triage findings, manage the vulnerability database, close coverage gaps and produce VEX documents, plus three agents that do not modify the project (triage, binary review, exposure analysis) and the configuration that connects the MCP server. The skills tell the agent which command and flags to use, and they carry the safety rules in [safety.md](https://github.com/owasp-dep-scan/dep-scan/blob/master/agent-plugin/reference/safety.md): untrusted projects stay untrusted, absolute paths, no installs or build scripts of the scanned project, and never a clean result that the scan manifest does not support.

The plugin lives in [`agent-plugin/`](https://github.com/owasp-dep-scan/dep-scan/tree/master/agent-plugin). It ships instructions, not the tool, so install dep-scan too (`pip install owasp-depscan`, or one of the other methods in the README). The skills are plain [Agent Skills](https://agentskills.io/specification), and the plugin has a root `plugin.json` in the [Agent Plugins](https://agent-plugins.org) format, so one folder serves every client below.

## What the skills cover

The six dep-scan-front skills cover what dep-scan's code delivers today. The eight toolchain skills reach the sibling analyzers directly for what dep-scan does not report yet (including the binary, memory-safety, mobile and crypto checks, which still exit 4 in dep-scan), and each one says so at the step; the mapping from questions to skills is in [the toolchain page](agent-skills-toolchain), and the tool lookup in the plugin's `reference/tools.md`.

| Skill | Use | Model-invocable |
| --- | --- | --- |
| `depscan-scan` | Scan a source project and report what to fix first, branching on the exit codes and the manifest stages | yes |
| `depscan-container-image` | Scan an image reference, rootfs or tar, with the cdxgen 13.8.0 minimum, the empty-findings trap an old cdxgen produces, and the rootfs link closure, trust material and installed-file provenance steps | yes |
| `depscan-triage` | Read a scan directory back, explain and rank findings; records no decisions, because the MCP server has no `record_triage` tool | yes |
| `depscan-vex-compliance` | Produce the CSAF VEX document a scan exports with `--csaf`, explain the `known_affected` and `under_investigation` statements dep-scan derives from reachability, and validate CSAF or VDR documents | yes |
| `depscan-vdb` | Check and refresh the vulnerability database, and answer advisory questions from the store with the v7 vdb CLI | no, on request |
| `depscan-coverage-loop` | Scan, read `depscan doctor` and the manifest's stages that did not complete, fix the missing tool, data or option each names, and re-scan | no, on request |
| `depscan-reachability-proof` | Prove or disprove reach for a finding with witness paths and root sets (golem, rusi, kosi, dosai, atom) | yes |
| `depscan-attack-surface` | Map exposure tiers, trust zones and the join to vulnerable packages (atom-tools, dosai) | yes |
| `depscan-change-risk` | Answer what changed between scans, builds or revisions (MCP `diff_scans`, dosai diff, atom-tools drift) | yes |
| `depscan-binary` | Review an executable, installer or driver with blint, with blintdb as a consent-gated tens-of-gigabytes download | yes |
| `depscan-mobile-app` | Analyse an APK, AAB or IPA with blint's deep mode, the JNI join, entitlements and privacy manifests | yes |
| `depscan-memory-safety` | Find memory-safety defects in C and C++ with atom and chen and rank them by reach; inventory unsafe boundaries elsewhere | yes |
| `depscan-supply-chain` | Audit install scripts, CI permissions, dependency sources, AI and MCP inventory (dep-scan's check, then cdx-audit's rule packs; predictive mode clones upstream and needs consent) | yes |
| `depscan-crypto` | Inventory cryptography and join it to reachability (golem, rusi, dosai, atom-tools, trustinspector) | yes |

For BOM generation the skills name the cdxgen plugin's skills (`sbom-generate`, `container-sbom`, `sbom-fidelity-loop`) instead of repeating cdxgen's commands; cdxgen has no MCP server, so everything there runs as a command line.

## Claude Code

Install:

```shell
claude plugin marketplace add owasp-dep-scan/dep-scan
claude plugin install depscan@depscan-plugins
```

Update with `claude plugin marketplace update depscan-plugins` followed by `claude plugin update depscan@depscan-plugins`.

Invoke a skill by describing the task, or by name as `/depscan:depscan-scan`. `depscan-vdb` and `depscan-coverage-loop` run only when you type their slash command, `/depscan:depscan-vdb` and `/depscan:depscan-coverage-loop`, because they change state. The `depscan:vuln-triager` agent preloads the triage, reachability-proof and attack-surface skills; the plugin also carries the `depscan:binary-reviewer` and `depscan:exposure-analyst` agents. None of the three modifies the project; they have Bash, so this rests on their instructions, and their analyzer reports go to `/tmp`.

Only Claude Code has these parts of the plugin:

- the three agents: `depscan:vuln-triager` for an existing scan directory, `depscan:binary-reviewer` for binaries and app artifacts, and `depscan:exposure-analyst` for exposure and reachability questions
- the `SessionStart` hook that warns when `depscan` is missing or older than the plugin, or when the `mcp` extra is missing, and the opt-in lockfile reminder hook (ZCode also runs both hooks)
- the `userConfig` options below, which Claude Code asks for when the plugin is enabled and substitutes into the skills as `${user_config.KEY}`

### The hooks

The hooks are standard-library Python and warn; they never install, never scan and never print secrets. They are launched in exec form (`python3` from `PATH`, the script as the argument), so a missing interpreter is Claude Code's documented non-blocking one-line status rather than a hook error. On the Windows VM the measured behavior is: `python3` there resolves to the Microsoft Store alias, which prints its one "Python was not found" line and exits without running the hook; with a real interpreter on `PATH` the hook runs and produces its warning JSON correctly (verified with the VM's `python.exe`). Windows users who see the Store line can disable the `python3` app-execution alias in Windows Settings or put a real `python3.exe` on `PATH`.

- `check_depscan.py` (`SessionStart`): warns once when `depscan` is not on `PATH`, is older than the plugin, or lacks the `mcp` extra its configured server needs. The version is read from the distribution metadata next to the binary, so the check has no side effects; a version it cannot read this way is accepted silently.
- `stale_lockfile.py` (`PostToolUse`, matcher `Write|Edit`): off unless the `lockfile_reminder` option is on, then reminds the agent once per file that the last scan is stale after it edits a lockfile or dependency manifest.

## Plugin settings

| Setting | Type | Meaning |
| --- | --- | --- |
| `lockfile_reminder` | boolean | Turn the stale-scan reminder hook on. Default off. |
| `vdb_home` | string | Directory for the vulnerability database, exported as `VDB_HOME`. |
| `vdb_flavor` | string | Value for `--vdb-flavor` and `depscan vdb download --flavor`: full, app-only, app-extended, app-10y or app-10y-extended. |
| `cdxgen_cmd` | string | How dep-scan starts cdxgen, exported as `CDXGEN_CMD`. dep-scan needs cdxgen 13.8.0 or newer. |
| `runtime` | string | `local` to run the depscan CLI from `PATH`, or `container` to run the ghcr.io/owasp-dep-scan/dep-scan image. |

No setting stores a key or token. There is no server URL setting: `depscan scan` has no option that takes a dep-scan server URL. The skills read `${user_config.KEY}` as plain text on clients without the feature and fall back to their defaults.

## Codex

Install from the terminal:

```shell
codex plugin marketplace add owasp-dep-scan/dep-scan
codex plugin add depscan@depscan-plugins
```

Codex reads `.agents/plugins/marketplace.json` in the repository and the portable `plugin.json` in `agent-plugin/`. Invoke a skill by naming it with a dollar sign, for example `$depscan-scan`, or describe the task. Codex ignores the hooks, the agents and `userConfig`; the skills then fall back to their defaults.

## Cursor

Cursor loads plugins that follow the Agent Plugins format, and its plugins reference describes a multi-plugin repository with `.cursor-plugin/marketplace.json` at its root, which this repository has. Plugins are installed and managed from Cursor's Customize page. Not yet tested.

## ZCode

```bash
zcode plugins marketplace add owasp-dep-scan/dep-scan
zcode plugins install depscan@depscan-plugins
zcode plugins list
```

ZCode reads `agent-plugin/.zcode-plugin/plugin.json`, which points at the same `skills/`, `hooks/hooks.json` and `.mcp.json` Claude Code uses. Without that file ZCode installs the plugin with its hooks only, so keep it in place when copying the plugin.

## Gemini CLI

Gemini CLI installs an extension from a directory that holds `gemini-extension.json` and a `skills/` folder, which is `agent-plugin/` here:

```shell
gemini extensions install ./agent-plugin
```

Not yet tested. The hooks, the agents and `userConfig` do not apply.

## Kiro

Kiro installs plugins as powers and reads the Agent Plugins `plugin.json`. In the IDE, import the power from a local path to `agent-plugin`; in Kiro CLI, `kiro-cli powers install /absolute/path/to/agent-plugin`. Not yet tested.

## opencode

opencode does not look inside plugin folders. It reads skills from the paths in its `skills` setting. Point that setting at the plugin's skills folder in `opencode.json`:

```json
{
  "$schema": "https://opencode.ai/config.json",
  "skills": {"paths": ["/absolute/path/to/dep-scan/agent-plugin/skills"]}
}
```

`opencode debug skill` then lists the fourteen skills (verified on opencode 1.19.6). The skills link to `../../reference/`, so keep the `reference/` folder beside `skills/`. The hooks, the agents and `userConfig` do not apply.

## Clients without a plugin MCP configuration

Claude Code reads `.mcp.json` at the plugin root and Codex reads `mcp.json`; the plugin ships both files with identical content, and neither passes `--allow-scans`. Cursor, Gemini CLI, Kiro, Copilot CLI and opencode have no documented way to read an MCP configuration from a plugin; point the client's own MCP settings at the server instead:

```json
{"mcpServers": {"depscan": {"command": "depscan", "args": ["mcp"]}}}
```

The server exits 4 when the `mcp` extra is missing; install it with `pip install "owasp-depscan[mcp]"`. The full tool list and the rules it enforces are in [the MCP server page](mcp).

## Privacy

The plugin sends nothing anywhere. It contains instructions, two Python hook scripts the client runs locally, and a configuration that starts `depscan mcp` on your machine. The tools it runs are the user's own dep-scan and its sibling tools, reading the user's own projects. A scan does use the network: it downloads the vulnerability database when the local one is missing, older than 48 hours or of another flavor (`--profile offline` prevents it), pulls the `ghcr.io/cdxgen/cdxgen` image for a source scan when `docker` is on `PATH`, `--bom-engine` is left on `auto` and there is no usable local cdxgen (`CDXGEN_CMD`, or a cdxgen on `PATH` at the minimum version, is used first; `--bom-engine CdxgenGenerator` always uses the local cdxgen), and lets golem fetch Go modules unless `--go-analyzer-network offline` is passed. The skills tell the agent to say which of these will happen before a scan.

## Keeping the manifests in step

`python -m contrib.gen_agent_manifests` writes the shared fields of every manifest from `pyproject.toml` and `contrib/agent_manifests_template.json`, and `python -m contrib.check_agent_plugin` fails when a file has drifted or a structural check does not hold. The pytest suite runs both over the repository, and the `Agent plugin` workflow runs them with Claude Code's own validator, pinned to an exact release, on every pull request that touches the plugin.
