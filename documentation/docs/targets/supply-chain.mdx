# Supply-chain checks

Most compromises of the last few years did not exploit a CVE. They came through a hijacked or malicious package, an install script, a private name squatting on a public registry, or a dependency whose maintenance had quietly stopped. The supply-chain check runs the audit for exactly those risks, beside the advisory matching that every scan does anyway.

## The check

```bash
depscan scan ./my-project --checks supply-chain --reports-dir reports
```

The check runs cdxgen's `cdx-audit` over the BOM the scan produced or was given. Its findings become `supply-chain` findings in `depscan.findings.json`, each with cdxgen's rule id, cdx-audit's severity and the component it names: install scripts (INT-001), a deprecated npm package (INT-005), a yanked Cargo crate (INT-010) or PyPI release (INT-030), a private name that exists on a public registry (INT-017 to INT-019), a version the registry does not list (INT-020 to INT-022), a package first published within the last year (INT-023 to INT-025), a package whose newest release is more than six years old (INT-026 to INT-028), and an npm version that ships or builds native code (INT-029). There is no risk score and no threshold: a package is listed when a rule matches it. The audit's own report is `cdx-audit-<type>.json` in the scan directory, and each finding's evidence is in `evidence.jsonl` with `cdx-audit` as the producer. The rule packs, the profiles that add the predictive mode and the options are on [the supply-chain audit reference](../reference/cli#the-supply-chain-audit).

The scan prints the findings as a Supply-Chain Audit Results table (rule, severity, the packages with the lockfile that declared them, and cdx-audit's message), which also lands in `depscan.txt` and `depscan.html` and which `depscan report` prints from a saved scan directory; `--no-vuln-table` leaves it out with the other tables. A container scan's crypto and rootfs findings are cdx-audit's too, but their categories are `crypto` and `binary-hardening`, so select on the producer to list everything the audit reported:

```bash
jq '.findings[] | select(.producer.name == "cdx-audit") | {category, rule, severity, components}' \
  reports/depscan.findings.json
```

Two things the check always does, whatever else runs: malicious-package advisories (`MAL-*`) are matched and reported at every version, and they are the top of the prioritization ladder when they are also reachable ([prioritization](../results/prioritization)). Private namespaces are checked for dependency-confusion exposure with `--private-ns appthreat,shiftleft`, naming the namespaces that must not exist in public.

## Where the check stops

The check needs `cdx-audit`, which the cdxgen npm package ships (cdxgen 13.10.0 or newer); `depscan doctor` reports it. `--checks supply-chain` on a machine without it exits 4 before any scan work, like any other check named in `--checks`. The `deep` and `research` profiles imply the check without naming it, so on such a machine they record it as a not-assessed `check-supply-chain` entry in the manifest, the way `--checks all` records the checks it cannot run, print one warning and run the rest of the profile.

Source and BOM scans audit the `package-integrity` and `dependency-source` rule packs, plus `cargo-security` when the BOM carries Cargo crates. Container scans (any of cdxgen's container type names, or a BOM whose root component is a container) add `container-risk`, `rootfs-hardening` and `cbom-security` to those packs. A BOM directory scan audits every BOM in the directory, and a lifecycle scan the documents each project type produced. Before the rules run, the audit looks the npm, PyPI and Cargo components up in their registries, one request per package, so it needs the network. The `deep` and `research` profiles add cdx-audit's predictive mode for a BOM that holds npm, PyPI or Cargo packages, which audits the required dependencies' upstream repositories under a target cap and a time budget; if it fails, the direct audit's findings stay and the failure is a coverage gap. Under the `offline` profile the audit makes no registry, git or OCI request, so the registry rules assess none of the packages. Whatever the audit could not assess (a predictive target it skipped, a registry lookup that did not run, a component no registry answered for) is a coverage reason on the findings and a `notAssessed` reason on the manifest's `risk` stage, never a clean result.

## AI and agent components

Projects that carry models, MCP servers or agent skills are inventoried by cdxgen's dedicated project types (`ai`, `mcp`, `ai-skill`), which produce the BOM components; dep-scan matches advisories against them like any other component. The rule packs that grade the configuration of those components land with the work above; scanning an AI project today tells you what is there, not yet whether its configuration is risky.

## Cryptographic assets

The `crypto` check is not implemented in this version and exits 4 when named ([coverage](../results/coverage)). The inventory half exists already: cdxgen writes cryptographic assets into the BOM's evidence, and atom-tools' reports name the algorithms and protocols a project uses. The agent plugin's `depscan-crypto` skill reaches those reports directly and says so at each step. What dep-scan will add, with [the crypto issue](https://github.com/owasp-dep-scan/dep-scan/issues/606), is the join from that inventory to findings and grades.
