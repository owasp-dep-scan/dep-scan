# dep-scan in CI

A CI job asks a scan three questions: did the scan actually run, what is new against last time, and does this pull request cross the line. dep-scan answers all three from files, which is what makes it scriptable: the JSON output is one document, the exit codes are documented, and the scan directory carries everything a later step or a human needs. The gate is the decisions file: it fails the build on the findings that matter and passes on the rest, with the decisions reviewed in the pull request itself. [The triage and gating page](../results/triage-and-gating) documents the file; this page shows the workflow shapes and says plainly what a gate does and does not prove.

## The image and the cache

The published image carries the toolchain, so the runner installs nothing. The image runs as the unprivileged user `owasp`, so run it as the runner's user to let it write into the mounted checkout, with `HOME` pointed at a writable directory for the tools' caches:

```yaml
- name: Scan dependencies
  run: |
    mkdir -p reports
    docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp -v "$PWD:/app" \
      ghcr.io/owasp-dep-scan/dep-scan:v7.0.0a4 \
      depscan scan /app --reports-dir /app/reports --profile ci
```

Pin the image to a dep-scan 7 tag such as `v7.0.0a4`. Only a final `vX.Y.Z` release moves the `latest` tag, so `latest` stays on dep-scan 6.x until 7.0.0 is released.

Mount or cache a directory as `VDB_HOME` and the database survives between jobs; without it, every job downloads the flavor again. Pin the database flavor for the job (`depscan vdb download --flavor app-only` as a step, or `vdb_flavor` in the config file), because a job that resolves a different flavor than the cache holds re-downloads.

## Profiles and what a CI scan runs

`--profile ci` is the job-shaped scan: vulnerability matching with reachability, explanations off, so no prompt file is written and the console stays small. [The profiles table](../targets/source-repositories#the-profiles) shows all five and the rule that explicit options win over the profile. `--fail-on-error` is the flag that stops a degraded scan from masquerading as a clean one: a failed analyzer, an unreadable reachability report or empty slices aborts the scan with a non-zero exit instead of reporting what it managed.

## Exit codes

The table is generated from the exit-code constant, and a test keeps this page in step with it:

<!-- exit code table start -->
| Code | Meaning |
| --- | --- |
| 0 | Success. |
| 1 | A scan or command that could not run, for example an unusable vulnerability database, a source target that does not exist, a baseline that cannot be read or does not match its digest, or a report on a scan whose recorded gate can no longer be evaluated. |
| 2 | A usage error, including any dep-scan 6 command line and a decisions file the schema refuses. |
| 3 | A decisions file expectation with action = "fail" matched a finding, so the gate the file (or --fail-on) describes is not met. |
| 4 | A requested capability cannot run, for example a named check whose analyzer is missing or an iOS or firmware target; or a decisions file [[require]] entry found the capability it names was not assessed, which wins over an expectation failure, because a gate over missing coverage cannot be trusted. |
<!-- exit code table end -->

Without a gate a scan that reports vulnerabilities exits 0, and a clean scan exits 0. Findings change the exit code only when the run has expectations, `[[expect]]` or `[[require]]` entries in the decisions file or `--fail-on`; triage entries, a baseline or a `--vex` document alone never do. Without expectations, exit code 0 means "the scan ran", never "everything is fine".

## Gating on findings

The gate is one options line or one file. A decisions file committed beside the code carries the policy, and `depscan scan` applies it and exits 3 when a fail-action expectation matches, 4 when a required capability was not assessed:

```yaml
- name: Scan and gate
  run: |
    depscan scan /app --reports-dir /app/reports --profile research \
      --fail-on "category=vulnerability,reach=reached"
```

`--fail-on` alone carries no coverage check: on a scan whose reachability did not run, `reach=reached` matches nothing and the step passes. The same policy lives in `.depscan/decisions.toml` when it needs review, together with the requirement that closes that gap:

```toml
[[expect]]
id = "no-reached-vulnerability"
description = "No vulnerability the project's code reaches"
category = "vulnerability"
reach = "reached"
action = "fail"

[[require]]
capability = "reachability"
```

The `[[require]]` entry is the part that keeps the gate honest: a `reach=reached` expectation over a scan whose reachability never ran matches nothing, so the requirement turns a silently skipped analyzer into exit 4. An expectation the run cannot evaluate, a `new` selector without a baseline among them, is reported as `not_evaluated` with the reason in `depscan.expectations.json`, never as a pass. The reach axis has a prerequisite worth restating: a scan of a Java or other JVM, JavaScript or TypeScript, Python, PHP or Ruby project answers reachability only when it runs cdxgen's research BOM profile (`--bom-profile research`, or `--profile research`). Go, Rust, Kotlin and .NET projects get reachability from a typed scan (`-t go`, `-t rust`, `-t kotlin` or `-t dotnet`) without the research profile, and Go, Rust and .NET also from `--profile deep` on a universal scan. That is why the examples on this page use `--profile research`; `--profile ci --bom-profile research` gives the same reachability without the license and supply-chain checks. Add `severity = "high"` to the expectation for a quieter gate. A `grade = "high"` floor matches only where the exposure axis is assessed, which today means .NET projects through dosai, because any axis that is not assessed caps the grade at moderate.

A gate over a saved scan needs no rescan: `depscan report <scan-dir>` re-evaluates the current decisions file against it, which is how a job gates a scan an earlier job made, and how a decision recorded after the scan takes effect. The result document lands in the scan directory as `depscan.expectations.json` at scan time; a report writes it only where `--out` names.

## What changed since last time

A baseline answers "is this pull request worse". `--baseline` names the reference scan for the run, a scan directory or a findings file relative to the working directory, and every finding the gate sees carries `new` or `existing` against it. The baseline on its own only marks the findings; an expectation with `new = true` and `action = "fail"` in the committed decisions file is what fails the build on exactly what the pull request added:

```toml
[[expect]]
id = "no-new-findings"
description = "Nothing new against the target branch"
new = true
action = "fail"
```

```yaml
- name: Scan and gate against the target branch
  run: |
    depscan scan /app --reports-dir /app/reports --profile research \
      --baseline /app/reports-base
```

Here `reports-base` is the target branch's scan directory, downloaded as an artifact or scanned in the same job. Pass the baseline on the command line rather than committing a `[baseline]` section to the decisions file: a committed `[baseline]` resolves against the decisions file's directory, and every scan on a checkout without that directory stops with exit 1. Without a baseline the `new` expectation is reported as `not_evaluated`, never as a pass. A baseline that cannot be read, or a `[baseline]` whose `digest` does not match, stops the run with exit 1 instead of marking everything new, so a stale baseline fails loudly. Two scans can also be compared without a gate, through the Python API (`api.diff`) or the MCP server's `diff_scans` tool, which key each vulnerability by the pair of its advisory id and the affected component ref; there is no `depscan diff` verb in this version. The API form, usable from a workflow step that already has Python:

```python
from depscan import api
old = api.load_scan("reports-base")
new = api.load_scan("reports-pr")
changes = api.diff(old, new)
print(len(changes.new), "new,", len(changes.fixed), "fixed")
```

Each list holds entries keyed by the pair of advisory id and affected component, and `changed` carries the pairs whose severity moved. Store the base branch's scan directory as an artifact and check it out for the comparison, or scan the base branch in the same job: check the pull request out into one directory and the base branch into a sibling, so each scan's root holds only its own tree (a source scan reads the whole tree it is given, and a nested checkout would leak baseline findings into the pull request's scan).

## Artifacts

Upload the scan directory, not only the console output. Everything a reviewer, an agent or the next job needs is in it:

```yaml
- uses: actions/upload-artifact@v4
  with:
    name: depscan-results
    path: reports/
```

## SARIF

dep-scan writes no SARIF in this version. The VDR is the interchange document for vulnerability data ([the VDR guide](vdr)), the findings file is the contract for everything else ([the finding model](../results/finding-model)), and code scanning upload of the results is [planned work](https://github.com/owasp-dep-scan/dep-scan/issues/590). Until it lands, the artifact above is what a reviewer opens.

## A pull request gate, end to end

Putting it together: scan on the pull request with the research profile so reachability is answered, fail on a degraded scan, gate on the reached vulnerabilities, and leave the scan directory for the reviewer. A committed `.depscan/decisions.toml` in the checkout is applied as well, and `--baseline` from the section above adds the comparison with the target branch:

```yaml
jobs:
  depscan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Pick a weekly cache key
        id: week
        run: echo "key=vdb-app-only-$(date -u +%G-%V)" >> "$GITHUB_OUTPUT"
      - name: Restore the vulnerability database
        uses: actions/cache@v4
        with:
          path: vdb-home
          key: ${{ steps.week.outputs.key }}
      - name: Scan and gate
        run: |
          mkdir -p vdb-home reports
          docker run --rm --user "$(id -u):$(id -g)" -e HOME=/tmp \
            -e VDB_HOME=/db -v "$PWD/vdb-home:/db" \
            -v "$PWD:/app" \
            ghcr.io/owasp-dep-scan/dep-scan:v7.0.0a4 \
            depscan scan /app -t js --profile research \
              --vdb-flavor app-only --reports-dir /app/reports --fail-on-error \
              --fail-on "category=vulnerability,reach=reached"
      - name: Show what the gate matched
        if: failure()
        run: |
          jq '.results[] | select(.status == "fail") |
              {id, action, findings}' reports/depscan.expectations.json
      - name: Upload the scan directory
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: depscan-results
          path: reports/
```

The cache key carries the ISO year and week, so the job starts from a fresh database at least once a week instead of reusing the first download forever, and the scan passes `--vdb-flavor app-only` so it reads the same flavor the key names (the default flavor is `full`). The `mkdir` line and the `--user` option matter because the image runs as the user `owasp`: without them the container cannot write into the directories Docker creates for the bind mounts, and `HOME=/tmp` gives the runner's user a writable home inside the container.

The server mode is the other shape of CI integration, a long-running service that many pipelines post scans to; it keeps every check of the command line and adds API key authentication, host and path allowlists, and request size limits ([the server page](server)).
